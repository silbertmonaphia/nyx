# PostgreSQL DDL 审查 — 2026-10-18

## 范围与方法

审查 Nyx 使用的三个 schema 中的所有表:

- `public` —— Go 后端,由 golang-migrate 管理(`backend/migrations/*.up.sql`)
- `agent` —— Python agent,由 Alembic 管理(`backend/agent_py/migrations/versions/*.py`)
- `langgraph` —— 由 LangGraph 的 `AsyncPostgresSaver.setup()` 创建(`langgraph/checkpoint/postgres/base.py`)

将列名、类型、可空性、默认值与实时开发库 `information_schema` 进行了核对。索引定义从迁移源码中审查(线上 `pg_indexes` 查询被环境权限规则拦截)。

**总体结论**:无 P0 级正确性缺陷。类型选择整体合理(`timestamptz`、`text`、`jsonb`、`uuid`、哈希用 `bytea`、`vector(1024)`)。真正的问题在于:(a) 索引与保留/清理查询不匹配,以及一处外键级联;(b) `public` 的时间戳列可空;(c) ID 类型不一致且缺少 `CHECK` 约束。

---

## `public`

### `users`

**合理之处**:`username` 唯一索引;`password_hash TEXT`(bcrypt);`deleted_at` 软删除;登录查询(`WHERE username = ? AND deleted_at IS NULL`)可使用该唯一索引。

**问题**:

- `id SERIAL` 是 `integer`,而 `feeds.user_id` 和 `agent.*.user_id` 是 `BIGINT`,`refresh_tokens.user_id` 是 `INTEGER`。当下不构成正确性 bug,但类型不一致。建议改为 `users.id BIGINT GENERATED BY DEFAULT AS IDENTITY`,并对齐 `refresh_tokens.user_id`。
- `created_at` / `updated_at` 在数据库中可空(迁移遗漏了 `NOT NULL`),而 `agent` 各表的时间戳均为 `NOT NULL`。补上 `SET NOT NULL`。
- `username UNIQUE` 覆盖软删除行。一旦账号删除被暴露,被释放的用户名将永远无法重用。若非本意,可改用 `UNIQUE (username) WHERE deleted_at IS NULL`。
- 用户名区分大小写(`Alice` 与 `alice` 是不同账号)。若希望大小写不敏感,可用 `UNIQUE INDEX ON users (lower(username))`,并在查询中使用 `lower(username) = lower($1)`。

### `refresh_tokens`

**合理之处**:仅存储 SHA-256 的 `token_hash`,本身已唯一;`family_id` 已建索引服务于家族吊销;`(user_id) WHERE revoked_at IS NULL` 偏索引支持在线计数/上限控制;自引用 `replaced_by_id` 建模了轮换链。

**问题**:

- **`replaced_by_id` 未建索引。** 其携带 `REFERENCES refresh_tokens(id) ON DELETE SET NULL`,因此每次清理删除被引用父行时,都会强制顺序扫描来清空子引用。需加上 `CREATE INDEX ON refresh_tokens (replaced_by_id);`。
- **`PurgeRefreshTokensOlderThan` 没有可用索引:** `WHERE created_at < cutoff AND (revoked_at IS NOT NULL OR expires_at < now())`。现有索引中无一包含 `created_at`,每次清理都是全表扫描。需加上 `CREATE INDEX ON refresh_tokens (created_at);`。无法建立基于过期的偏索引,因为 `now()` 不是 immutable。
- `ListOldestActiveRefreshTokensByUser` 按 `created_at` 排序;可将偏索引扩展为 `(user_id, created_at) WHERE revoked_at IS NULL`,一次性同时覆盖计数与排序。

### `feeds`

**合理之处**:归属外键配合 `feeds_user_id_idx`;软删除;两个三字母 GIN 索引服务于 title/description 的 `ILIKE '%x%'`;审计时间戳完整。

**问题**:

- 分页查询为 `WHERE user_id = ? AND deleted_at IS NULL ORDER BY created_at DESC, id DESC`,而索引却是单独的 `user_id` 索引和全局 `created_at` 索引。在每用户 feed 较多时会对该用户的子集做排序。建议:
  `CREATE INDEX feeds_user_created_idx ON feeds (user_id, created_at DESC, id DESC) WHERE deleted_at IS NULL;`
  这一索引同时服务于 `QueryFeedsPage`、`QueryFeedsPageAsc`(反向扫描)与 `CountFeeds`。
- `idx_movies_active ON feeds(id) WHERE deleted_at IS NULL` 没有被任何查询使用(id 查询走主键)。建议移除。
- 表重命名后,索引名仍为 `idx_movies_*`,序列仍为 `movies_id_seq`。仅为维护问题,可后续迁移中重命名。
- `created_at` / `updated_at` 可空,建议收紧。
- `user_id` 外键未指定 `ON DELETE` 动作(默认 NO ACTION)。软删除用户没问题,但未来一旦加入硬删除/抹除路径,该 FK 会成为阻碍;需明确决策。

### `feed_embeddings`

**合理之处**:`feed_id` 同时是主键与外键(与 `feeds` 一对一,带 `ON DELETE CASCADE`);`vector(1024)` 匹配嵌入模型;HNSW + `vector_cosine_ops`;冗余的 `user_id` 在 join 两端都加了过滤;`content_hash` 避免重复调用嵌入接口。`Indexer.Delete` 在 feed 软删除时会移除该行,因此表内不会积累垃圾数据。

**问题**:

- HNSW + `WHERE user_id = ?` 是 **post-filter**(后置过滤)。在多租户索引中,某用户的向量只占总体的极小部分,ANN 扫描可能返回的候选数达不到 `LIMIT`。单用户规模下问题不大;规模扩大后,应使用 pgvector iterative scan(`hnsw.iterative_scan = relaxed_order`)或按 user 进行分区。
- `user_id` 没有外键(这是跨边界有意为之),也没有强制其匹配 `feeds.user_id` 的约束;写入路径加双端过滤读取是当前的事后防线,可接受。
- `vector` 维度无法原地修改;更换模型需另一次 drop/recreate 迁移(在 000015 中已经处理过一次)。这是已知成本。

## `agent`

### `agent.runs`

**合理之处**:UUID 主键即为 run id;`(user_id, started_at DESC)` 服务于按用户列出与按用户 GDPR 删除;`(last_heartbeat_at) WHERE status = 'running'` 偏索引精准服务于陈旧 run 清理;`ended_at` / `archived_at` 可空。

**问题**:

- **保留策略没有可用索引:** `DELETE ... WHERE ended_at < cutoff AND status IN ('completed', 'failed')` 没有任何现有索引覆盖。建议:
  `CREATE INDEX runs_terminal_ended_idx ON agent.runs (ended_at) WHERE status IN ('completed', 'failed');`
- `status TEXT` 无 `CHECK` 约束,任何值都可写入。建议补 `CHECK (status IN ('running', 'completed', 'failed'))`。
- `archived_at` 目前是死字段:没有任何代码读写它(为未来的软删除/GDPR 拆分预留)。保留无妨,但不参与任何查询或索引。
- 缺少 `session_id`(用于将每个 turn 的 run 关联到会话)。这个已知问题已由 `openspec/changes/agent-per-turn-run-ids/` 跟进。

### `agent.chat_sessions`

**合理之处**:`(user_id, last_active_at DESC) WHERE deleted_at IS NULL` 精准匹配侧边栏查询;所有时间戳均为 `NOT NULL`;两阶段软删除/硬删除保留模型清晰。

**问题**:

- **两阶段保留都做全局扫描:**
  - 阶段 1 `UPDATE ... WHERE last_active_at < cutoff AND deleted_at IS NULL`:现有索引以 `user_id` 开头,无法直接范围扫描 `last_active_at`。
  - 阶段 2 `DELETE ... WHERE deleted_at IS NOT NULL AND deleted_at < cutoff`:该偏索引恰好排除了软删除行,完全无法使用。
  建议:
  ```sql
  CREATE INDEX chat_sessions_last_active_idx ON agent.chat_sessions (last_active_at) WHERE deleted_at IS NULL;
  CREATE INDEX chat_sessions_deleted_idx    ON agent.chat_sessions (deleted_at)    WHERE deleted_at IS NOT NULL;
  ```
- GDPR 路径 `DELETE FROM chat_sessions WHERE user_id = $1`(不带 `deleted_at` 谓词)无法使用偏索引,因此是全表扫描。抹除操作频率低,可接受;若在意可加一普通 `(user_id)` 索引。
- 把 `id` 复用为 `run_id` 是当前 bug 的根因,待定的 OpenSpec 变更正在解决。

### `agent.chat_messages`

**合理之处**:`BIGINT IDENTITY` 主键;带 `ON DELETE CASCADE` 的外键;`(session_id, created_at)` 精准服务于回放;`tool_calls` / `steps` 以 `JSONB` 存储以支持结构化回放;`prompt_tokens` / `completion_tokens` 可空,用以区分遗留行与真实的 provider 零值。

**问题**:

- `role TEXT` 无 `CHECK`。当下只写入 `user` / `assistant`;建议加 `CHECK (role IN ('user', 'assistant'))`(后续若引入 `tool` / `system` 行再扩展)。
- 同一事务内插入的多条消息共享同一 `created_at`(`now()` 取自事务开始时间);顺序依赖 `id` 的 tiebreaker。查询已按 `id ASC` 排序,因此是正确的;若把 `id` 加入索引可减少 tie 排序,但收益有限。
- 删除走 session 外键;引用侧索引(以 `session_id` 开头)支持级联。设计正确。

### `agent.chat_user_prefs`

**合理之处**:唯一索引 `(user_id, key)` 是 `ON CONFLICT` 的目标;`(user_id, updated_at DESC)` 服务于注入式读;`value JSONB`;`source_session_id` 故意不建外键是合理的。

**问题**:

- `source_session_id` 未建索引;`delete_prefs_for_sessions` 与 `delete_orphaned` 都是扫全表。表很小,优先级低;可考虑 `(source_session_id) WHERE source_session_id IS NOT NULL`。
- `key TEXT` 无长度/格式约束;至少应限制长度,防止异常 key 让索引膨胀。
- 代理主键 `id` 没有被任何查询使用;无害但冗余。

### `agent.data_audit_log`

**合理之处**:两个索引精准覆盖按用户读取与保留扫描;`payload_summary` 只存计数不存内容;`requested_at` 是保留锚点。

**问题**:

- "仅追加" 只是应用层约定。应用角色既可 `UPDATE` 也可 `DELETE`(保留策略需要 DELETE),任何代码路径都可能篡改审计行。如需更强的证据链,可加触发器阻止 UPDATE,或拆出仅插入角色。可选的加固。
- `action TEXT` 无 `CHECK`。实际值仅为 `export` / `erase`;建议加约束。

## `langgraph.*`(库托管)

- 类型合理:`JSONB` 表示状态,`BYTEA` 表示大块二进制,`TEXT` 表示 thread/checkpoint id。
- `checkpoints`、`checkpoint_blobs`、`checkpoint_writes` 上额外的 `(thread_id)` 索引与各自主键前缀重复(所有 PK 以 `thread_id` 开头)。是冗余的写放大,但来自 LangGraph 固定的 `setup()` DDL,不要手工修改。
- `checkpoint_writes` 目前是最大的表(~20 MB / 35k 行)。保留 cron 调用 `adelete_thread`,会清理三张 checkpoint 表;方向正确,留意清理吞吐。

- `agent.alembic_version` —— Alembic 修订锚点;`version_table_schema='agent'` 把它放在 `agent` schema 中。

## 优先级建议

### P1 —— 数据量增长后会影响性能

1. `refresh_tokens (replaced_by_id)` 与 `refresh_tokens (created_at)`。
2. `agent.runs (ended_at) WHERE status IN ('completed', 'failed')`。
3. `agent.chat_sessions (last_active_at) WHERE deleted_at IS NULL` 与 `(deleted_at) WHERE deleted_at IS NOT NULL`。
4. `feeds (user_id, created_at DESC, id DESC) WHERE deleted_at IS NULL`。

### P2 —— 一致性与纵深防御

5. 将 `users.id` / `refresh_tokens.user_id` 对齐到 `BIGINT`。
6. 给 `users.created_at`、`users.updated_at`、`feeds.created_at`、`feeds.updated_at` 补 `NOT NULL`。
7. 为 `runs.status`、`chat_messages.role`、`data_audit_log.action` 加 `CHECK` 约束。
8. 清理遗留的 `idx_movies_*` / `movies_id_seq` 命名,并评估下线未被使用的 `idx_movies_active`。

### P3 —— 规模化与安全加固

9. 解决 pgvector HNSW 在多租户规模下的 post-filter 召回问题(iterative scan 或分区)。
10. 跨 schema 隔离目前仅为 `search_path` 级别:agent 与后端当前共用同一个数据库角色,因此 agent 仍可通过全限定名访问 `public.*`。要做到真正隔离,需要分离角色并撤销 `public` 上的权限。

## P1 迁移草稿

```sql
-- public
CREATE INDEX IF NOT EXISTS idx_refresh_tokens_replaced_by_id
    ON refresh_tokens (replaced_by_id);
CREATE INDEX IF NOT EXISTS idx_refresh_tokens_created_at
    ON refresh_tokens (created_at);
CREATE INDEX IF NOT EXISTS feeds_user_created_idx
    ON feeds (user_id, created_at DESC, id DESC)
    WHERE deleted_at IS NULL;

-- agent
CREATE INDEX IF NOT EXISTS runs_terminal_ended_idx
    ON agent.runs (ended_at)
    WHERE status IN ('completed', 'failed');
CREATE INDEX IF NOT EXISTS chat_sessions_last_active_idx
    ON agent.chat_sessions (last_active_at)
    WHERE deleted_at IS NULL;
CREATE INDEX IF NOT EXISTS chat_sessions_deleted_idx
    ON agent.chat_sessions (deleted_at)
    WHERE deleted_at IS NOT NULL;
```

注:`agent.*` 的语句应放在 Alembic 修订中,而不是 golang-migrate 迁移;此处并列展示仅为阅读清晰。
