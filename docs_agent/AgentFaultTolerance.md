# Nyx Agent — Fault Tolerance Index

Every place the agent stack can fail, what happens today, and what should happen if a future slice re-prioritises it. Living document — when a fault class moves from "unaddressed" to "covered", update the table; when a new fault class appears (new tool, new LLM, new bridge), add a row.

## Why most of the agent's fault tolerance is "retry" — and what that misses

Every covered row in the table above is a retry-style fix: try again, with the same input (transient) or with a corrected input (validation). This is the cheapest fix the agent layer can apply because it has no infrastructure to manage — no circuit breakers, no bulkheads, no fallback queues, no auto-scaling. The Python agent process is invoked by the Go backend; its only recovery verbs are "ask the model again" and "wait and call the bridge again".

That leaves four classes of failure that retry alone cannot solve:

1. **Model quality** — the model emits a plausible-looking but ungrounded answer. There is no failure signal the system can recognise; the run reaches `done` cleanly. This is hallucination, not a fault. Addressed by output evaluation, not retry. (See rows 6 and 16.)

2. **Persistent external failures** — the bridge is down for an hour. Retry up to the cap and the run fails; we cannot auto-recover the bridge. Addressed by infra (auto-restart, health checks). The agent layer can only do "fail-closed with a typed error".

3. **State corruption / loss** — checkpoint writes fail or resume state is unreadable. We can mint a fresh `run_id` and continue, but the previous run's history is gone. Addressed by stronger DB resilience, not retry. (See rows 8 and 14.)

4. **Quota / cost caps** — the user's budget is hit mid-run. Fail-closed by design. Addressed by product decisions (raise the cap, prompt the user) not by infra. (See rows 4 and 5.)

A future "real" fault-tolerance slice for the agent layer would have to add at least one non-retry primitive: a circuit breaker that short-circuits the tool-call site after N consecutive failures (giving the user a fast "tools are down" answer instead of waiting for the retry budget to exhaust); or a fallback tool registry (a cached read-only mode) for the registry-unavailable case (row 20). Both are bigger than the current slice's blast radius.

## What this slice (`agent-tool-dispatch-retry`) actually changes

- **Adds**: surfaces #2, #3, #13, #15 get explicit retry semantics with the `agent-tool-retry` capability.
- **Adds**: a partial-failure user-visible signal (`<PartialFailureBanner>`) for surfaces #2, #3, #4, #5, #9, #10, #13, #15 (any system-recognised failure other than `run_metadata_unavailable` and RAG empty).
- **Does NOT add**: surfaces #6, #11, #12, #14, #16, #17, #19, #20. Each is a separate future slice if re-prioritised.

The partial-failure banner is the user-facing payoff: today, a user receiving a "best-effort continue" answer cannot tell whether the run was clean or whether the model filled in gaps. After this slice, the answer carries a banner naming the failed step(s) — the user knows when to trust the answer and when to re-prompt.

## What `agent-stale-run-sweeper` changes (2026-10-14)

- **Adds a sweep surface with no row in the table above**: zombie `running` rows (crash / kill / `agent_unavailable` — row 17's aftermath) are reaped to `failed` / `error_code='stale_run'` after `PYTHON_AGENT_STALE_RUN_TIMEOUT_SECONDS` (default 900s) of heartbeat silence. The timeout is also the window in which a crashed run remains resumable by echoing its `run_id`; after reaping, resume follows the terminal-row path (`fresh_run`).
- **Closes the checkpoint-GC half of rows 8/17's aftermath**: retention now deletes each removed run's langGraph checkpoint thread via `adelete_thread` (langGraph ships no retention of its own). The sweeper deliberately preserves checkpoint data — a reaped run's thread is collected with the row at retention time.
- **Does NOT change the wire**: no new SSE frame kind or error code; `stale_run` is a DB `error_code` only. Resume semantics inside the window are byte-for-byte unchanged.
- **First-writer-wins**: heartbeat touches and reaps are conditional on `status='running'`; a live process's terminal write stays authoritative and clears a premature `stale_run` (`mark_completed` sets `error_code=NULL`).
