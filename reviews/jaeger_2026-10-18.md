# Jaeger 保留期与持久化 Review — 2026-10-18

## Scope & method

- 当前 compose 里的 `jaeger` 服务：`jaegertracing/jaeger:2.18.0`（`docker-compose.yml:92`）
- 容器内**没有** config 文件（只有 `/cmd/jaeger/jaeger-linux` 和 `sampling-strategies.json`），因此运行的是镜像内嵌的默认配置；已对照 v2.18.0 仓库的 `cmd/jaeger/config.yaml` 核实
- 实测容器：UI `:16686` 返回 200；`/api/services` 已有 `nyx-backend`、`nyx-agent`、`nyx-e2e-side` 的 trace
- 容器以 UID 10001 / GID 0 运行
- SDK 采样：Go 后端 `ParentBased(AlwaysSample())`（`backend/internal/platform/observability/tracing.go:107`）；agent 与 frontend 未配置 sampler（OTel 默认 AlwaysOn）

## 当前能保留多久

默认配置用的是**内存存储**：

- `jaeger_storage.backends.some_store.memory.max_traces: 100000`（主存储），archive 存储同样 100k
- **没有时间维度的 TTL**，也没有挂 volume

实际保留期是「以下两者先到者」：

1. 容器重启 → 全丢（无持久化）
2. 写满 100,000 条 trace → 最老的被静默淘汰

100k trace 能撑多久取决于流量（一条 trace ≈ 一次请求链路）。UI 里 Lookback 默认 1h 只是**查询过滤窗口**，不是保留期——查旧数据要把 Lookback 调到 24h 或自定义时间范围。

## 会不会压缩失真

不会，Jaeger 没有指标那种 rollup/降采样：

- trace 按整条链路原样存储，span 全量；被保留的数据就是精确数据，老数据不会"越压越糙"
- 落盘后端（Badger / ES）的压缩是**无损**的（ES 段压缩、Badger zstd/snappy），不影响查询结果
- 真正的"丢数据"只有三种，且都不是压缩造成的：
  - **内存淘汰**：超过 100k 条，最老的直接消失，没有汇总保留
  - **重启清空**
  - **SDK 侧采样**：采样发生在 span 产生时。当前没有这个问题——Go 后端 `ParentBased(AlwaysSample())`，agent 和前端未设 sampler 即默认 AlwaysOn，100% 采集。Jaeger v2 默认配置里的 `adaptive_sampling` processor 只统计 root span 用于计算 remote sampling 概率，**本身不丢 trace**
  - 以后如果开了比率采样或 tail sampling，才会"缺数据"，那是策略不是失真

## 持久化选项

| 后端 | 保留机制 | 适用 |
|---|---|---|
| **Badger**（嵌入式磁盘 KV） | 配置 `ttl.spans: 336h` 之类，挂 volume | 单机，dev/小规模，最省事 |
| **Elasticsearch / OpenSearch** | Jaeger 自身不管删，靠 ILM：按天 rollover + delete phase | 生产标准，可水平扩展 |
| **Cassandra** | keyspace/表级 TTL | 大规模，运维重 |
| **ClickHouse** | 实验性后端（feature gate） | 不建议生产 |
| **Remote storage（gRPC）** | jaeger-remote-storage 独立服务 + PostgreSQL | 查询/采集分离 |
| **OTLP 导出到 Tempo / Sentry / Grafana Cloud** | 由目标系统定保留期 | 长期低成本；但 Jaeger UI 查不到，Tempo 要用 Grafana 看 |

注意事项：

- Jaeger 的 "archive" 存储**不会自动归档**，是 UI 里手动点 archive 才写入，不能当保留策略用
- ES/OpenSearch 的索引删除必须配 ILM（例如 `jaeger-main-*` 保留 14 天），Jaeger 不负责删

## 本地最省事的改法：Badger + volume

写一个 `jaeger/config.yaml`：

```yaml
service:
  extensions: [jaeger_storage, jaeger_query, healthcheckv2]
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [jaeger_storage_exporter]

extensions:
  healthcheckv2:
    use_v2: true
    http:

  jaeger_query:
    storage:
      traces: main

  jaeger_storage:
    backends:
      main:
        badger:
          directories:
            keys: /jaeger/keys
            values: /jaeger/values
          ephemeral: false
          ttl:
            spans: 336h

receivers:
  otlp:
    protocols:
      grpc:
      http:

processors:
  batch:

exporters:
  jaeger_storage_exporter:
    trace_storage: main
```

compose 里改 `jaeger` 服务：

```yaml
  jaeger:
    image: jaegertracing/jaeger:2.18.0
    command: ["--config=/etc/jaeger/config.yaml"]
    volumes:
      - ./jaeger/config.yaml:/etc/jaeger/config.yaml:ro
      - ./data/jaeger:/jaeger
```

坑：容器以 **UID 10001 / GID 0** 运行，宿主目录要先创建并授权，否则 Badger 写不进去：

```bash
mkdir -p data/jaeger
sudo chown -R 10001:0 data/jaeger
```

## 长期方案建议

如果目标是长期、跨机器保留，按既有的可观测性方案做 collector 双写：保留 `jaeger_storage_exporter` 给本地 UI，再加一个 `otlphttp` exporter 发 Tempo（对象存储，按租户配 `block_retention`）或 Sentry（按套餐保留期）。Jaeger 只是其中一份短期副本。
