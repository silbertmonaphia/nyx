# Jaeger 保留期与持久化 Review — 2026-10-18

## Scope & method

- 当前 compose 里的 `jaeger` 服务：`jaegertracing/jaeger:2.18.0`（`docker-compose.yml:92`）
- 容器内**没有** config 文件（只有 `/cmd/jaeger/jaeger-linux` 和 `sampling-strategies.json`），因此运行的是镜像内嵌的默认配置；已对照 v2.18.0 仓库的 `cmd/jaeger/config.yaml` 核实
- 实测容器：UI `:16686` 返回 200；`/api/services` 已有 `nyx-backend`、`nyx-agent`、`nyx-e2e-side` 的 trace
- 容器以 UID 10001 / GID 0 运行
- SDK 采样：Go 后端 `ParentBased(AlwaysSample())`（`backend/internal/platform/observability/tracing.go:107`）；agent 与 frontend 未配置 sampler（OTel 默认 AlwaysOn）

## 线上可用性结论

**不够。** 当前 compose / k8s 里的 Jaeger 只能承担 dev/staging 的「看链路」用途，不能作为线上排障的 trace 后端。问题不在 Jaeger 本身（v2 就是 OTel Collector 发行版），而在这套部署缺了四个生产必需项：持久化存储、Collector pipeline（采样/脱敏/重试/fan-out）、HA 副本、以及与 metrics/logs 的关联。逐项差距见文末「线上化差距」与「上线最小清单」。

## 当前能保留多久

默认配置用的是**内存存储**：

- `jaeger_storage.backends.some_store.memory.max_traces: 100000`（主存储），archive 存储同样 100k
- **没有时间维度的 TTL**，也没有挂 volume

实际保留期是「以下两者先到者」：

1. 容器重启 → 全丢（无持久化）
2. 写满 100,000 条 trace → 最老的被静默淘汰

100k trace 能撑多久取决于流量（一条 trace ≈ 一次请求链路）。UI 里 Lookback 默认 1h 只是**查询过滤窗口**，不是保留期——查旧数据要把 Lookback 调到 24h 或自定义时间范围。

## 会不会压缩失真

不会，Jaeger 没有指标那种 rollup/降采样：

- trace 按整条链路原样存储，span 全量；被保留的数据就是精确数据，老数据不会"越压越糙"
- 落盘后端（Badger / ES）的压缩是**无损**的（ES 段压缩、Badger zstd/snappy），不影响查询结果
- 真正的"丢数据"只有三种，且都不是压缩造成的：
  - **内存淘汰**：超过 100k 条，最老的直接消失，没有汇总保留
  - **重启清空**
  - **SDK 侧采样**：采样发生在 span 产生时。当前没有这个问题——Go 后端 `ParentBased(AlwaysSample())`，agent 和前端未设 sampler 即默认 AlwaysOn，100% 采集。Jaeger v2 默认配置里的 `adaptive_sampling` processor 只统计 root span 用于计算 remote sampling 概率，**本身不丢 trace**
  - 以后如果开了比率采样或 tail sampling，才会"缺数据"，那是策略不是失真

## 持久化选项

| 后端 | 保留机制 | 适用 |
|---|---|---|
| **Badger**（嵌入式磁盘 KV） | 配置 `ttl.spans: 336h` 之类，挂 volume | 单机，dev/小规模，最省事 |
| **Elasticsearch / OpenSearch** | Jaeger 自身不管删，靠 ILM：按天 rollover + delete phase | 生产标准，可水平扩展 |
| **Cassandra** | keyspace/表级 TTL | 大规模，运维重 |
| **ClickHouse** | 实验性后端（feature gate） | 不建议生产 |
| **Remote storage（gRPC）** | jaeger-remote-storage 独立服务 + PostgreSQL | 查询/采集分离 |
| **OTLP 导出到 Tempo / Sentry / Grafana Cloud** | 由目标系统定保留期 | 长期低成本；但 Jaeger UI 查不到，Tempo 要用 Grafana 看 |

注意事项：

- Jaeger 的 "archive" 存储**不会自动归档**，是 UI 里手动点 archive 才写入，不能当保留策略用
- ES/OpenSearch 的索引删除必须配 ILM（例如 `jaeger-main-*` 保留 14 天），Jaeger 不负责删

## 本地最省事的改法：Badger + volume

写一个 `jaeger/config.yaml`：

```yaml
service:
  extensions: [jaeger_storage, jaeger_query, healthcheckv2]
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [jaeger_storage_exporter]

extensions:
  healthcheckv2:
    use_v2: true
    http:

  jaeger_query:
    storage:
      traces: main

  jaeger_storage:
    backends:
      main:
        badger:
          directories:
            keys: /jaeger/keys
            values: /jaeger/values
          ephemeral: false
          ttl:
            spans: 336h

receivers:
  otlp:
    protocols:
      grpc:
      http:

processors:
  batch:

exporters:
  jaeger_storage_exporter:
    trace_storage: main
```

compose 里改 `jaeger` 服务：

```yaml
  jaeger:
    image: jaegertracing/jaeger:2.18.0
    command: ["--config=/etc/jaeger/config.yaml"]
    volumes:
      - ./jaeger/config.yaml:/etc/jaeger/config.yaml:ro
      - ./data/jaeger:/jaeger
```

坑：容器以 **UID 10001 / GID 0** 运行，宿主目录要先创建并授权，否则 Badger 写不进去：

```bash
mkdir -p data/jaeger
sudo chown -R 10001:0 data/jaeger
```

## 长期方案建议

如果目标是长期、跨机器保留，按既有的可观测性方案做 collector 双写：保留 `jaeger_storage_exporter` 给本地 UI，再加一个 `otlphttp` exporter 发 Tempo（对象存储，按租户配 `block_retention`）或 Sentry（按套餐保留期）。Jaeger 只是其中一份短期副本。

## 线上化差距（2026-10-19 补充）

### 采样策略与文档不一致

- `backend/internal/platform/observability/tracing.go:107` 显式传入 `sdktrace.WithSampler(sdktrace.ParentBased(sdktrace.AlwaysSample()))`。
- OTel Go SDK v1.46.0（`backend/go.mod:32`）的 `WithSampler` 文档明确写着：该 option **覆盖** `OTEL_TRACES_SAMPLER` / `OTEL_TRACES_SAMPLER_ARG`（`sdk@v1.46.0/trace/provider.go:418-419`）。
- 因此 `tracing.go:103-105` 的注释「SDK still honours OTEL_TRACES_SAMPLER … operators can flip to traceidratio without recompiling」和 `FUTURE_BACKEND.md:57` 的「SDK honours `OTEL_TRACES_SAMPLER`」都不成立。线上改采样率必须改代码重新发版。
- 现状是 100% 采集：后端 `ParentBased(AlwaysSample)`，agent 与前端未配置 sampler（OTel 默认 AlwaysOn）。与 100k trace 的内存上限叠加，高流量下可观测窗口很短。

### 缺少 OTel Collector 层

- 三个 SDK（Go 后端、Python agent、浏览器）都直连 Jaeger 的 OTLP receiver：`docker-compose.yml` 中 backend/agent 的 `OTEL_*` / `PYTHON_AGENT_OTEL_ENDPOINT` 环境变量、`frontend/nginx.conf:81` 的 `/otlp/` 代理。
- 缺的是一层可编程 pipeline：
  - `memory_limiter` + `batch` + `retry`：背压与重试，避免 Jaeger 重启/过载时 SDK 队列被打满后静默丢 span；
  - `tail_sampling`：error / 慢请求 100% 保留，其余按 5–10% 采样（当前只有全采或全丢）；
  - attribute 脱敏：LLM prompt/completion、user id、token 等敏感字段应在 collector 删除，而不是依赖每个 SDK 自觉；
  - fan-out：同一份 span 同时写 Jaeger（短期 UI）+ Tempo/Sentry（长期保留），这是既定目标拓扑的落点。
- 成本提示：Jaeger v2 本身就是 OTel Collector 发行版，可以在同一进程加 pipeline（改 config），也可以独立部署 `otel-collector` 再转发给 Jaeger；后者更利于多环境/多租户路由。

### 单副本与容量

- k8s：`k8s/jaeger-deployment.yaml` 单副本、256Mi 内存上限、无 PVC；backend 3 副本、frontend 2 副本，trace 后端是单点。
- 无状态 Jaeger 重启即丢全部 trace（默认内存存储），且没有采集/查询分离。
- compose 的 `mem_limit: 512m` 与 100k trace 上限哪个先到取决于 span 大小；OOM 后容器重启（`restart: always`）同样清空。
- 生产规模下需要：Badger + volume（单机小规模）或 ES/ClickHouse/Tempo（可水平扩展）。

### 指标、日志与 trace 的割裂

- 后端已暴露 `/metrics`（`backend/cmd/api/main.go:214`，Prometheus middleware 打点），但 compose 和 `k8s/` 里没有 Prometheus/Grafana，metrics 无人 scrape。
- 日志写 stdout，Logging middleware 已带 `trace_id`/`span_id`，但没接 Loki/Fluent Bit/collector，无法按 trace_id 联动查询。
- 结论：当前所谓「OTel 实现」只覆盖 traces；完整的线上可观测栈还缺 metrics 存储/告警和 logs 聚合。

### 安全与暴露面

- compose 把 `16686`（UI）和 `4318`（OTLP HTTP）绑到 `0.0.0.0`（`docker-compose.yml:97-99`），无 TLS、无认证，仅应作为 dev 使用。
- k8s 中 Jaeger Service 是 ClusterIP，UI 未进 Ingress；但 `app.nyx.com` 通过 frontend nginx 的 `location /otlp/`（`frontend/nginx.conf:81`）把 OTLP 写入口公开暴露且无认证。任何客户端都能 POST 伪造 span：污染 trace 数据，也可用洪泛快速打满 100k 内存上限，使真实的近期 trace 被静默淘汰（可观测性 DoS）。上线前应关闭公网 `/otlp/`，或加 token/限流。
- 目标拓扑下，浏览器 span 应走 Sentry（已有 DSN gate）或经带鉴权的 collector，不经裸 Jaeger。

### 与既定目标拓扑的偏差

此前确认的混合可观测方向是：frontend → Sentry（errors/replay/sourcemaps）；backend/agent → OTel Collector → OTLP 双写 Sentry + Tempo（trace_id 通过 W3C traceparent 对齐）。当前仓库实现是 SDK 直连 Jaeger，没有 Collector 层，也没有后端 trace 写入 Sentry；`SENTRY.md` 仍写着「Backend stays on OTel→Jaeger」。Jaeger 在这个目标拓扑里只是本地短期副本，不是线上主存储。

## 上线最小清单

按性价比排序：

1. **持久化**：单机先把 Jaeger 换到 Badger + volume + `ttl.spans`（见「本地最省事的改法」的 config 示例）；多副本规模直接上 ES/ClickHouse 或 Tempo。
2. **加 Collector pipeline**：`memory_limiter` + `batch` + `retry` + `tail_sampling`（error/slow 全留，其余 5–10%）+ 敏感 attribute 删除；同时作为 Sentry/Tempo 双写的 fan-out 点。
3. **采样策略可配置**：移除或参数化 `tracing.go:107` 的硬编码 `WithSampler`；修正 `tracing.go:103-105` 注释与 `FUTURE_BACKEND.md:57` 的错误描述。
4. **接上 metrics/logs**：部署 Prometheus 抓 `/metrics` + Grafana 看板/告警；日志接 Loki（或 collector logs pipeline），按 `trace_id` 关联。
5. **收紧入口**：关闭或鉴权 `app.nyx.com/otlp/`；OTLP 入口加 TLS/token；Jaeger UI 仅内网或加认证。
6. **HA**：collector 与存储后端至少 2 副本（或采集/查询分离），消除 Jaeger 单点。
