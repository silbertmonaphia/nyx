# PostgreSQL DDL Review — 2026-10-18

## Scope & method

Reviewed every table in the three schemas used by Nyx:

- `public` — Go backend, managed by golang-migrate (`backend/migrations/*.up.sql`)
- `agent` — Python agent, managed by Alembic (`backend/agent_py/migrations/versions/*.py`)
- `langgraph` — created by LangGraph's `AsyncPostgresSaver.setup()` (`langgraph/checkpoint/postgres/base.py`)

Column names, types, nullability and defaults were compared against the live dev database's `information_schema`. Index definitions were reviewed from the migration sources (the live `pg_indexes` query was blocked by the environment's permission rules).

**Overall verdict:** no P0 correctness defects. Type choices are sound overall (`timestamptz`, `text`, `jsonb`, `uuid`, `bytea` for hashes, `vector(1024)`). The real issues are (a) indexes that do not match the retention/purge queries and one foreign-key cascade, (b) `public` timestamps that are nullable, and (c) inconsistent ID types and missing `CHECK` constraints.

---

## `public`

### `users`

**Sound:** `username UNIQUE`, `password_hash TEXT` (bcrypt), `deleted_at` soft delete; the login query (`WHERE username = ? AND deleted_at IS NULL`) can use the unique index.

**Issues:**

- `id SERIAL` is `integer`, while `feeds.user_id` and `agent.*.user_id` are `BIGINT` and `refresh_tokens.user_id` is `INTEGER`. No correctness bug today, but the types are inconsistent. Prefer `users.id BIGINT GENERATED BY DEFAULT AS IDENTITY` and align `refresh_tokens.user_id`.
- `created_at` / `updated_at` are nullable in the database (the migration omitted `NOT NULL`), unlike the `agent` tables where all timestamps are `NOT NULL`. Add `SET NOT NULL`.
- `username UNIQUE` covers soft-deleted rows. If account deletion is ever exposed, that username can never be reused. If that is not the intent, use `UNIQUE (username) WHERE deleted_at IS NULL`.
- Usernames are case-sensitive (`Alice` and `alice` are distinct accounts). If case-insensitive identity is desired, use `UNIQUE INDEX ON users (lower(username))` and query with `lower(username) = lower($1)`.

### `refresh_tokens`

**Sound:** stores only the SHA-256 `token_hash`, which is unique; `family_id` is indexed for family revocation; `(user_id) WHERE revoked_at IS NULL` is a partial index for active-count/cap enforcement; the self-referencing `replaced_by_id` models the rotation chain.

**Issues:**

- **`replaced_by_id` has no index.** It carries `REFERENCES refresh_tokens(id) ON DELETE SET NULL`, so every purge deletion of a referenced parent row forces a sequential scan to null the child references. Add `CREATE INDEX ON refresh_tokens (replaced_by_id);`.
- **`PurgeRefreshTokensOlderThan` has no usable index:** `WHERE created_at < cutoff AND (revoked_at IS NOT NULL OR expires_at < now())`. None of the current indexes contain `created_at`, so each cleanup is a full table scan. Add `CREATE INDEX ON refresh_tokens (created_at);`. A partial index on expiry is not possible because `now()` is not immutable.
- `ListOldestActiveRefreshTokensByUser` orders by `created_at`; extending the partial index to `(user_id, created_at) WHERE revoked_at IS NULL` covers both the count and the ordering in one index.

### `feeds`

**Sound:** ownership FK plus `feeds_user_id_idx`, soft delete, two trigram GIN indexes serving `ILIKE '%x%'` on title/description, complete audit timestamps.

**Issues:**

- Pagination is `WHERE user_id = ? AND deleted_at IS NULL ORDER BY created_at DESC, id DESC`, but the indexes are a standalone `user_id` index and a global `created_at` index. With many feeds per user this sorts the user's subset. Prefer:
  `CREATE INDEX feeds_user_created_idx ON feeds (user_id, created_at DESC, id DESC) WHERE deleted_at IS NULL;`
  The same index serves `QueryFeedsPage`, `QueryFeedsPageAsc` (backward scan) and `CountFeeds`.
- `idx_movies_active ON feeds(id) WHERE deleted_at IS NULL` is not used by any query (id lookups use the PK). Candidate for removal.
- After the table rename, index names are still `idx_movies_*` and the sequence is still `movies_id_seq`. Maintenance-only issue; rename in a later migration.
- `created_at` / `updated_at` are nullable; tighten them.
- The `user_id` FK has no `ON DELETE` action (default NO ACTION). Soft-deleted users are fine, but a future hard-delete/erasure path will be blocked by `feeds`; decide this explicitly.

### `feed_embeddings`

**Sound:** `feed_id` is both PK and FK (1:1 with `ON DELETE CASCADE`), `vector(1024)` matches the embedding model, HNSW with `vector_cosine_ops`, denormalized `user_id` filtered on both sides of the join, `content_hash` avoids redundant embedding API calls. `Indexer.Delete` removes the row when a feed is soft-deleted, so the table does not accumulate garbage.

**Issues:**

- HNSW + `WHERE user_id = ?` is a **post-filter**. In a multi-tenant index where one user's vectors are a tiny fraction of the total, an ANN scan may return fewer than `LIMIT` rows. Fine at single-user scale; at scale, use pgvector iterative scan (`hnsw.iterative_scan = relaxed_order`) or partition by user.
- `user_id` has no FK (intentional cross-boundary design) and nothing enforces that it matches `feeds.user_id`; the write path plus double-sided retrieval filtering is the current safeguard, acceptable as-is.
- The `vector` dimension cannot be changed in place; a model change requires another drop/recreate migration (already handled once in 000015). This is a known cost.

## `agent`

### `agent.runs`

**Sound:** UUID primary key is the run id; `(user_id, started_at DESC)` serves listing and per-user GDPR deletion; the partial `(last_heartbeat_at) WHERE status = 'running'` index precisely serves the stale-run sweeper; `ended_at` / `archived_at` are nullable.

**Issues:**

- **Retention has no index:** `DELETE ... WHERE ended_at < cutoff AND status IN ('completed', 'failed')` is not covered by any existing index. Add:
  `CREATE INDEX runs_terminal_ended_idx ON agent.runs (ended_at) WHERE status IN ('completed', 'failed');`
- `status TEXT` has no `CHECK`; any value can be written. Add `CHECK (status IN ('running', 'completed', 'failed'))`.
- `archived_at` is currently dead: no code reads or writes it (reserved for a future soft-delete/GDPR split). Keeping it is fine, but it participates in no query or index.
- Missing `session_id` (linking each turn's run to its conversation). This is the known issue already covered by `openspec/changes/agent-per-turn-run-ids/`.

### `agent.chat_sessions`

**Sound:** `(user_id, last_active_at DESC) WHERE deleted_at IS NULL` exactly matches the sidebar query; all timestamps are `NOT NULL`; the two-phase soft-delete/hard-delete retention model is clear.

**Issues:**

- **Both retention phases do global scans:**
  - Phase 1 `UPDATE ... WHERE last_active_at < cutoff AND deleted_at IS NULL`: the existing index leads with `user_id`, so it cannot range-scan `last_active_at` directly.
  - Phase 2 `DELETE ... WHERE deleted_at IS NOT NULL AND deleted_at < cutoff`: the partial index excludes soft-deleted rows, so it cannot be used at all.
  Add:
  ```sql
  CREATE INDEX chat_sessions_last_active_idx ON agent.chat_sessions (last_active_at) WHERE deleted_at IS NULL;
  CREATE INDEX chat_sessions_deleted_idx    ON agent.chat_sessions (deleted_at)    WHERE deleted_at IS NOT NULL;
  ```
- GDPR `DELETE FROM chat_sessions WHERE user_id = $1` (without a `deleted_at` predicate) cannot use the partial index, so it is a full scan. Erasure is low-frequency, so this is acceptable; add a plain `(user_id)` index if it matters.
- Reusing `id` as `run_id` is the root of the current bug; the pending OpenSpec change addresses it.

### `agent.chat_messages`

**Sound:** `BIGINT IDENTITY` primary key, FK with `ON DELETE CASCADE`, `(session_id, created_at)` exactly serves replay, `tool_calls` / `steps` stored as `JSONB` for structured replay, nullable `prompt_tokens` / `completion_tokens` distinguish legacy rows from a real provider zero.

**Issues:**

- `role TEXT` has no `CHECK`. Only `user` / `assistant` are written today; add `CHECK (role IN ('user', 'assistant'))` (expand later if `tool` / `system` rows are introduced).
- Multiple messages inserted in one transaction share the same `created_at` (`now()` is transaction start); ordering relies on the `id` tiebreaker. The queries already order by `id ASC`, so this is correct; adding `id` to the index would reduce tie sorting but is low value.
- Deletion goes through the session FK; the referencing-side index (leading `session_id`) supports the cascade. Correct design.

### `agent.chat_user_prefs`

**Sound:** the unique `(user_id, key)` index is the `ON CONFLICT` target; `(user_id, updated_at DESC)` serves the injection read; `value JSONB`; the deliberate absence of an FK on `source_session_id` is justified.

**Issues:**

- `source_session_id` has no index; `delete_prefs_for_sessions` and `delete_orphaned` both scan the table. The table is small, so this is low priority; consider `(source_session_id) WHERE source_session_id IS NOT NULL`.
- `key TEXT` has no length/format constraint; at minimum cap the length so an anomalous key cannot bloat the index.
- The surrogate `id` primary key is not used by any query; harmless but redundant.

### `agent.data_audit_log`

**Sound:** two indexes precisely cover per-user reads and the retention sweep; `payload_summary` stores counts only, never content; `requested_at` is the retention anchor.

**Issues:**

- Append-only is only an application-level convention. The application role can both `UPDATE` and `DELETE` (retention needs DELETE), so any code path could modify audit rows. For a stronger chain of evidence, add a trigger that blocks UPDATE, or split out an insert-only role. Optional hardening.
- `action TEXT` has no `CHECK`. The actual values are `export` / `erase`; add a constraint.

## `langgraph.*` (library-managed)

- Types are fine: `JSONB` for state, `BYTEA` for large blobs, `TEXT` for thread/checkpoint ids.
- The extra `(thread_id)` indexes on `checkpoints`, `checkpoint_blobs` and `checkpoint_writes` duplicate the primary-key prefixes (all PKs lead with `thread_id`). They are redundant write amplification, but they come from LangGraph's fixed `setup()` DDL; do not hand-edit them.
- `checkpoint_writes` is currently the largest table (~20 MB / 35k rows). The retention cron calls `adelete_thread`, which cleans all three checkpoint tables; the direction is correct, but keep an eye on cleanup throughput.

## Infrastructure tables

- `public.schema_migrations` (`version`, `dirty`) — golang-migrate bookkeeping.
- `agent.alembic_version` — Alembic revision anchor; `version_table_schema='agent'` places it in the `agent` schema.

No issues.

## Prioritized recommendations

### P1 — will hurt as data grows

1. `refresh_tokens (replaced_by_id)` and `refresh_tokens (created_at)`.
2. `agent.runs (ended_at) WHERE status IN ('completed', 'failed')`.
3. `agent.chat_sessions (last_active_at) WHERE deleted_at IS NULL` and `(deleted_at) WHERE deleted_at IS NOT NULL`.
4. `feeds (user_id, created_at DESC, id DESC) WHERE deleted_at IS NULL`.

### P2 — consistency and defence in depth

5. Align `users.id` / `refresh_tokens.user_id` to `BIGINT`.
6. Add `NOT NULL` to `users.created_at`, `users.updated_at`, `feeds.created_at`, `feeds.updated_at`.
7. Add `CHECK` constraints for `runs.status`, `chat_messages.role`, `data_audit_log.action`.
8. Clean up stale `idx_movies_*` / `movies_id_seq` names and evaluate dropping the unused `idx_movies_active`.

### P3 — scale and security hardening

9. Address pgvector HNSW post-filter recall at multi-tenant scale (iterative scan or partitioning).
10. Cross-schema isolation is `search_path`-level only: the agent and backend currently use the same database role, so the agent can still reach `public.*` with fully qualified names. True isolation needs separate roles and revoked `public` privileges.

## Suggested P1 migration sketch

```sql
-- public
CREATE INDEX IF NOT EXISTS idx_refresh_tokens_replaced_by_id
    ON refresh_tokens (replaced_by_id);
CREATE INDEX IF NOT EXISTS idx_refresh_tokens_created_at
    ON refresh_tokens (created_at);
CREATE INDEX IF NOT EXISTS feeds_user_created_idx
    ON feeds (user_id, created_at DESC, id DESC)
    WHERE deleted_at IS NULL;

-- agent
CREATE INDEX IF NOT EXISTS runs_terminal_ended_idx
    ON agent.runs (ended_at)
    WHERE status IN ('completed', 'failed');
CREATE INDEX IF NOT EXISTS chat_sessions_last_active_idx
    ON agent.chat_sessions (last_active_at)
    WHERE deleted_at IS NULL;
CREATE INDEX IF NOT EXISTS chat_sessions_deleted_idx
    ON agent.chat_sessions (deleted_at)
    WHERE deleted_at IS NOT NULL;
```

Note: the `agent.*` statements belong in an Alembic revision, not a golang-migrate migration; they are shown together here only for readability.
