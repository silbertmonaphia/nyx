# Redis 设计 Review — 2026-10-18

## Scope & method

审查范围：当前 `mvp` 树上所有 Redis 使用点与部署配置，不含 Langfuse 自带的独立 `langfuse-redis`。

- Go 缓存层：`backend/internal/platform/cache/cache.go`、`backend/internal/feed/service.go`、`backend/cmd/api/main.go`
- Python agent：`backend/agent_py/agent/{budget,approvals,approvals_api,main,config}.py`
- 部署：`docker-compose.yml`、`k8s/redis-deployment.yaml`、`k8s/backend-deployment.yaml`、`k8s/secrets.yaml.example`
- 测试：`backend/internal/platform/cache/*_test.go`、`backend/internal/feed/service_test.go`
- 实测环境：`redis:7-alpine`（live 版本 7.4.11），`127.0.0.1:6380 -> 6379`，容器名 `nyx-redis-1`

实测命令与结果：


## 总评

核心设计是对的：cache-aside、per-user key、请求路径 best-effort、agent 侧 fail-closed、SCAN+UNLINK 失效、真实 Redis 集成测试。

主要风险不在这套读写逻辑，而在**同一个 Redis 承担了两种可用性契约**（Go 侧“挂了也无所谓”，agent 侧“挂了就停服”），以及**无认证、无内存上限、配置校验缺口**。

## 当前使用面

| 使用方 | 用途 | Key | 类型 / 操作 | TTL |
|---|---|---|---|---|
| Go backend | feed 列表缓存 | `feeds:u={uid}:q={query}:p={page}:s={size}:o={sort}` | JSON `Page`，`GET`/`SET` | `CACHE_TTL`（默认 5m） |
| Go backend | 失效 | `feeds:u={uid}:` 前缀 | `SCAN` + `UNLINK` | — |
| Go backend | 健康检查 | — | `PING` | — |
| Python agent | 每用户每小时 token 预算 | `agent:budget:u={uid}:h={YYYYMMDDHH}`（UTC） | `INCRBY` / `DECRBY` / `EXPIRE` | 每次检查重置 90m |
| Python agent | 审批意图 | `approval_intent:{run_id}:{approval_id}` | `SET` 值为到期时间 | 窗口 300s + 30s margin |
| Python agent | 审批决策 | `approval_decision:{run_id}:{approval_id}` | `SET NX` 先到先得 | 同上 |
| Python agent | 健康检查 | — | `PING` | — |

所有 key 都在 **DB 0**。Go 侧当前实测 `cache=noop`（`REDIS_ENABLED=false`），真正在读写 Redis 的是 Python agent。

## 做得好的

- key 带 userID，读写和失效都是用户作用域，跨用户泄漏在缓存层被结构性地挡住（`feed/service.go:127,263,274`），并有专门的隔离测试（`service_test.go:185` 起）。
- 失效用 `SCAN` + `UNLINK` 而非 `KEYS`/`DEL`（`cache.go:139-160`）；命中/未命中/错误有 Prometheus 计数器 `cache_operations_total`。
- 缓存值 JSON 解码失败时回源而不是 500；所有 cache 错误只 `log.Warn`，从不失败请求。
- agent 侧语义严格：预算不可用时拒绝 LLM 调用；审批在 intent 缺失/过期/存储不可达时一律 deny，`SET NX` 先到先得，从不自动批准（`approvals.py` 文件头有完整说明）。
- 测试覆盖了 TTL、前缀失效、noeviction、ping 失败、容器重启重连（`cache_integration_test.go`）。
- 限流器（Go 中间件、chat、MCP）明确选择进程内实现，没有伪装成 Redis 分布式限流（`chat/ratelimit.go` 注释说明了取舍）。

## 高

### H1 Redis URL 明文进日志

`backend/cmd/api/main.go:145`

```go
log.Info().Str("url", cfg.RedisURL).Msg("Cache enabled")
```

k8s 的 `REDIS_URL` 来自 Secret，一旦写成 `redis://:password@host:6379`，密码直接进日志。

**Fix**：只打 scheme/host/db，或对 userinfo 做 redact。

### H2 可选缓存变成启动硬依赖

`backend/cmd/api/main.go:137-148`、`:691-704`

请求路径把缓存当 best-effort，但启动时 `connectRedisWithRetry` 重试 10 次（每次 1s）后 `log.Fatal`。Redis 故障期间 backend 重启/滚动发布会直接起不来，与“缓存可选”的契约矛盾。

**Fix**：默认退化为 noop + 告警，另设 `REDIS_REQUIRED=true` 才允许 fatal；至少把这个契约写进配置文档。

### H3 无认证 Redis 暴露在 default 网络

`docker-compose.yml:55-82`、`:436`、`:628`

Redis 同时挂 `default` + `internal`，没有 `requirepass`；frontend、vllm、jaeger 都在 `default`。任何 default 网络容器或本机进程都能读写全部 key，风险不止缓存：

- `approval_decision:*` 可被伪造 → 审批门形同虚设
- `agent:budget:*` 可被重置
- `feeds:*` 可被投毒

fail-closed 只防“读不到”，防不了“可写”。

k8s 同样：`k8s/secrets.yaml.example:15` 是 `redis://redis:6379`（无密码），ClusterIP、无 NetworkPolicy。

**Fix**：Redis 只挂 `internal`（backend 已是双网卡，不受影响）；生产加 ACL/密码 + TLS + NetworkPolicy。

## 中

### M1 无 maxmemory，缓存与安全状态共用 db0

`docker-compose.yml:57`、`k8s/redis-deployment.yaml:21`

容器 `mem_limit: 256m`，但 Redis `maxmemory 0`。feed key 基数 = 用户 × 不同 query（最长 200 字符），打满会被 cgroup OOM kill，连带预算/审批一起挂。共用 db0 还意味着 `FLUSHDB`/备份恢复不分缓存和安全状态。

**Fix**：设 `maxmemory`（留 headroom）+ `noeviction`（不能静默 evict 审批/预算 key）；缓存考虑放 DB1 或独立实例。

### M2 CACHE_TTL 未校验 > 0

`backend/internal/platform/config/config.go:450`、`cache.go:127`

只做 `ParseDuration`。go-redis 在 TTL 为 0（及 -1 以外的负数）时发不带过期的 `SET` → `CACHE_TTL=0s` 会让 feed 缓存永久驻留。

**Fix**：校验 `> 0` 并设上限。

### M3 客户端超时/重试未配置，故障时不“快失败”

- Go：`cache.NewRedis` 用 go-redis 默认（dial 5s、read/write 3s、`MaxRetries=3`）。Redis 慢或黑洞时，一次 feed 读可能先卡数秒再回源，重试还会放大。缓存应 fail fast：read/write 100–500ms、重试 0–1。
- Python：`Redis.from_url(..., decode_responses=True)`（`agent_py/agent/main.py:324`）没设 `socket_timeout` / `socket_connect_timeout`。黑洞地址会挂到 OS TCP 超时，预算检查和审批等待会“卡很久才 fail closed”。

### M4 预算计数非原子 + 失败调用也扣额度

`backend/agent_py/agent/budget.py:76-108`

`INCRBY` 和 `EXPIRE` 是两条命令，中间崩溃/断连会留下无 TTL 的 key；`DECRBY` 若发生在 key 过期后会重建一个负值无 TTL key。空闲用户之后不再访问就永久泄漏。

**Fix**：Lua 一次完成 `INCRBY + EXPIRE`（含条件回滚），或先 `SET 0 EX ttl NX` 再 INCRBY。

另外预扣的是固定 `DEFAULT_ESTIMATED_TOKENS=1000`（`executor.py:70`），只在 `exceeded` 时回滚；LLM 调用本身失败（超时、`_step_runtime_error`）不回滚，失败也消耗额度。确认是否有意。

### M5 敏感文本进 key

`backend/internal/feed/service.go:274`、`backend/agent_py/agent/budget.py:41`

原始搜索词和 userID 明文在 key 中，会出现在 `MONITOR`/`SLOWLOG`/RDB/备份里。userID 已在 `docs/agent-deployment.md:142` 按 pseudonymous 说明；搜索词可能含个人信息。

**Fix**：query 先 SHA-256 再入 key（保留前缀可读性）。

## 低

### L1 读→失效→Set 竞态

`backend/internal/feed/service.go:106` 已有注释，TTL 兜底，可接受。若要更强一致性，用 per-user version key（读带版本、写时递增、旧 key 自然过期），同时把失效从 O(keyspace) 降到 O(1)。

### L2 DeletePrefix 是全库 SCAN

`cache.go:139-160`。不是按用户索引；key 总量大后每次写都扫全库，并发写还可能漏删（TTL 兜底）。当前规模 OK。

### L3 无 jitter / singleflight

固定 TTL 无抖动，热门页集中过期时会并发打 DB。可加 ±10–20% jitter，必要时 singleflight。

### L4 Go 侧 IncrBy/Expire 是死接口

`cache.go:52-53,171-180` 没有生产调用方（agent 用自己的 Python client），只有测试在测（`cache_test.go:174`）。要么删掉，要么接上真正的消费方——否则测试绿灯会让人误以为 Go 预算链路存在。

### L5 可观测性

有 `cache_operations_total`，但没有 Redis 内存/eviction/延迟指标和告警。`/api/health` 的 `cache_ping` 不影响整体 status（对可选缓存合理），agent `/healthz` 失败即 503（对硬依赖合理）——两种语义是自洽的，但要显式监控后者。

### L6 文档漂移

- `docker-compose.yml:64-66` 说 “no persistence (no --save, no AOF)”，实际默认 RDB 保存点是开的（实测 `save 3600 1 300 100 60 10000`、`rdb_saves:17`），只是落在 tmpfs → 事实上的临时存储。
- `CLAUDE.md` 的 key 格式仍写 `feeds:q=...:p=...:s=...`，实际是 `feeds:u={uid}:q=...:o=...`。
- `README.md:96` 称 Redis 为 “optional cache”，但对 Python agent 的 budget/approvals 是硬依赖。

### L7 k8s AOF 的取舍

`k8s/redis-deployment.yaml:21` 用 `--appendonly yes` + PVC。现有数据都可重建/自过期，AOF 主要价值是让暂停中的审批跨重启存活；代价是磁盘 churn 和启动 replay。保留可以，但应写明目的并补 `maxmemory`。

### L8 大小写 query 产生重复 key

Postgres 用 `ILIKE`（`backend/queries/feeds.sql:21-22`），缓存 key 却大小写敏感 → `Foo` 和 `foo` 各存一份。key 里 normalize 成小写可减少基数。

## 建议顺序

1. **立刻**：H1（脱敏）、M2（TTL 校验）、M3（超时）、L6（文档）——小改动，直接降风险。
2. **尽快**：H3（网络/认证边界）、H2（启动依赖语义）。
3. **随后**：M1（maxmemory/隔离）、M4（Lua 原子计数 + 失败计费确认）。
4. **规模上来再做**：L1/L2（version key）、L3（jitter）、L4（清理死接口）、M5（key 哈希）。

## 结论

逻辑层没有明显正确性缺陷。主要设计债是“一个无认证、无上限的 Redis 同时承载可选缓存和强安全语义的审批/预算状态”，以及故障时 Go 与 agent 两套相反的可用性契约没有被显式化。
