# 12-Factor App 与 Nyx 对照（2026-10-18）

12-Factor App（原 https://12factor.net）的 12 条，按顺序：

| # | Factor | 一句话 | Nyx 现状 |
|---|---|---|---|
| I | Codebase | 一个代码库，多份部署 | ✅ 单 monorepo，按包 semantic-release |
| II | Dependencies | 显式声明并隔离依赖 | ✅ `go.mod` / `package-lock.json` / venv / Dockerfile |
| III | Config | 配置放环境变量 | ✅ viper + `.env`；⚠️ `VITE_*` 在构建期内联进 bundle（前端固有限制） |
| IV | Backing services | 数据库/缓存等当可挂载资源 | ✅ PG/Redis/Jaeger 全走 URL/env，可替换 |
| V | Build, release, run | 构建、发布、运行严格分离 | ⚠️ 构建/发布分离，但 Go 迁移在后端启动时跑；agent 的 `agent-migrate` 一次性服务才是标准做法 |
| VI | Processes | 无状态进程 | ✅ API 无状态，会话/状态在 PG/Redis；⚠️ 限流器、chat backfill 的 `sync.Map` 是进程内状态 |
| VII | Port binding | 自己监听端口导出服务 | ✅ 8080 / 9000 / nginx |
| VIII | Concurrency | 靠进程模型横向扩展 | ⚠️ 可横向扩，但 per-IP 限流器是每实例内存态，多副本会放大配额 |
| IX | Disposability | 快速启动、优雅退出 | ✅ `main.go:281` 有 graceful shutdown；agent 有 lifespan 清理 |
| X | Dev/prod parity | 开发/预发/生产尽量一致 | ⚠️ 本地后端/前端跑宿主机、基础设施跑 Docker；vLLM 还有 host vs compose 两套 |
| XI | Logs | 日志是事件流，应用不管存储 | ⚠️ 详见 `reviews/log_stream_2026-10-18.md` |
| XII | Admin processes | 管理任务作为一次性进程跑 | ⚠️ refresh-token cleanup、限流器 GC 都是 API 进程里的 goroutine，不是 one-off；agent 的迁移/retention 更接近标准 |

最值得留意的是 **V、VIII、XII** 这三条在分布式部署下会真的咬人（启动时迁移的竞态、限流不共享、后台任务被每个副本重复执行），XI 则是上一份 review 的内容。

# 12-Factor 今天还成立吗？有没有更好的？

**结论：仍然是一个好的基线，但更像“宪法”而不是“完整法律”。** 它没有过时到该被替换，也没有任何一个后继标准获得了同等共识。“更好”取决于负载类型——对 Nyx 这种无状态 HTTP + SPA + agent 的组合，12-Factor 依然应该作为默认基线，但需要叠加几层现代标准。

## 为什么它仍然成立

12-Factor 的核心不是具体技术，而是**把应用和执行环境解耦**：配置进环境、端口绑定、无状态进程、日志是事件流、进程可随时启停。这恰好是容器 / Kubernetes / Serverless 时代最值钱的约束——2011 年在 Heroku 上总结的东西，在 K8s 上反而更贴切。其中几条预测性很强：

- **III Config** — 环境变量注入，就是今天 K8s ConfigMap/Secret 的模型
- **IX Disposability** — 快速启动 + 优雅退出，就是 liveness probe 和滚动发布的前提
- **XI Logs** — “应用只管往 stdout 写，收集是平台的事”，就是今天 sidecar/collector 架构
- **VI Processes** — 无状态进程，就是水平扩缩容的前提

而且它刻意不碰代码架构（DDD、六边形、微服务都能用），所以不会和其他设计原则冲突。

## 明显的盲区

它诞生于 2011 年的 PaaS 世界观，默认“平台会兜底”，因此缺了今天最贵的几块：

| 盲区 | 现在的对应物 |
|---|---|
| 安全（认证、授权、密钥、供应链） | OWASP ASVS、SLSA、SBOM、NIST SSDF |
| 可观测性（metrics / traces / SLO） | OpenTelemetry、SRE / error budget |
| API 契约与版本化 | API-first、OpenAPI、gRPC/protobuf |
| 有状态负载（DB、ML、流处理） | K8s Operator / StatefulSet、DataOps |
| 多租户、成本、数据驻留/合规 | 各家 Well-Architected、FinOps |
| 异步/事件驱动（幂等、重试、顺序） | 消息队列/事件溯源实践 |
| AI agent 工作负载 | 12-Factor Agents、OTel GenAI semconv、MCP/A2A |

## 直接可用的“升级版”

1. **Beyond the Twelve-Factor App（15-Factor，Kevin Hoffman，2016）** — 最直接的升级：保留原 12 条，新增 **API first**、**Telemetry**、**Authentication & Authorization**。对 Nyx 来说这三条都已经在做（huma/OpenAPI、OTel+Prometheus、JWT），所以 15-Factor 比原版更贴合。
2. **云厂商 Well-Architected Framework**（AWS 六支柱 / Azure / GCP）— 更偏组织级清单：运维卓越、安全、可靠性、性能、成本、可持续性。适合做季度评审，不适合当日常编码规范。
3. **SRE / Production Readiness Review** — 补上 SLI/SLO、error budget、故障演练、on-call。12-Factor 完全不谈“上线后怎么判断好坏”。
4. **OpenTelemetry semantic conventions** — 事实标准，补上 XI 只说了“日志是流”但没规定字段/关联方式的那一半。
5. **12-Factor Agents（HumanLayer，2025）** — 专门针对 LLM agent：own your control flow、own your context window、tools are structured outputs、unify execution/business state、launch/pause/resume、contact humans via tool calls、stateless reducer 等。这一套和 `backend/agent_py` 的设计高度重合（显式 planner/executor、确认卡、按 run_id 恢复、Postgres checkpoint），可以直接当 checklist 做一次审计。

## 对 Nyx 的建议

- 继续拿 **12-Factor 当基线**，但把评审清单升级成 **15-Factor**（补 API-first / telemetry / authN-Z）。
- **安全**单独用 OWASP ASVS + SLSA/SBOM，别指望 12-Factor。
- **可观测性**以 OTel semantic conventions 为准，日志格式统一后接 collector——这正是 `reviews/log_stream_2026-10-18.md` 里的差距。
- **agent 服务**额外跑一遍 12-Factor Agents，它比 12-Factor 更贴近这个服务的真实风险（上下文管理、控制流、人机协作、状态一致性）。

一句话：**12-Factor 没有被淘汰，但它只是“可部署性”这一层；今天需要的是它 + 15-Factor + Well-Architected/SRE + 安全标准 + 领域标准（agent）的组合。**
