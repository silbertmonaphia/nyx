# Proposal

## Why

The agent planner silently does not do what the user asked. On the 2026-10-16 baseline, 「总结最近3个月我发的feed，**形成一篇新feed发出去**」 planned `[rag, llm]` — it drafted the feed text and never called `create_feed`. The fresh 2026-10-21 baseline at `c482adc` shows a different failure: the planner now plans `[rag, llm, create_feed, llm]`, the compose `llm` runs, and `create_feed` executes with `ok: true` — but its description is a plan-time placeholder (「对用户过去三个月发布的内容进行归纳与分析，提炼核心主题和趋势。」), not the rag summary. The case still scores 0/3 because the corpus expects the stale strict `[rag, create_feed, llm]` shape. The user gets a published feed whose body is generic; the score's reason changed, the user-visible defect did not. The same missing-write defect still costs `main-all-tools-combined` (plans `[rag, web_search, llm]`). Separately, on 「今天天气如何？**上网搜索看看**」 it plans `[react, llm]`; the loop calls `web_search` and receives the stub rows, then the final `llm` step answers 「我无法直接访问互联网…」 because a react step's internal tool results are not carried into the next `llm` step's context.

All three are visible as 0/3 case-level breaches in both the committed 2026-10-16 baseline (`evals/artifacts/20261016T095807Z/`) and the fresh baseline (`evals/artifacts/20261021T174740Z/`), both overall 0.73 = 24/33 graded, 3 skipped. The fresh run used the Makefile's overall floor of 0.7; the 2026-10-16 artifact recorded 0.85. The per-case breaches are identical. None of them is caught by any other gate: the deterministic test layers all pass, and the eval suite that does catch them **runs nowhere** — it is not in CI, it last ran 2026-10-16, and `bugs.md`, which tracked all three as open, was deleted on 2026-10-19 while they were still red.

**The baseline also contains a defect this proposal originally missed.** `main-rag-update-feed` and `main-rag-delete-feed` report 3/3, but their recorded samples show every write call failing schema validation: `update_feed` was called with `id: "feed_id_from_list"` where the schema wants a number, and `delete_feed` was called with `{"feed_id": "list_feeds_3months"}` — wrong key, and the value is a plan step id. The executor's retry substituted `list_feeds` (read-only); the fresh run's query is `"negative emotion"` and returns `total: 0` because `list_feeds.query` is a literal `ILIKE '%query%'` and the mood fixtures are Chinese. `step_end` reported `status: "ok"`, and no feed was updated or deleted. Two assertions passed: plan-shape equality, and `no_destructive_tool_call` — which is not an outcome check but an authorization check whose `allowed_tools` whitelist contains exactly the tool the case intends to call, so its pass is guaranteed by construction rather than observed. Nothing in `evals/graders/` asserts that a `tool_call` produced `tool_result.ok == true`.

**And the agent told the user it succeeded.** With zero writes executed, the fresh update case answered 「已根据你的请求，将你近3个月中关于负面情绪的Feed内容…更新为积极情绪表达…」 and the delete case answered 「已根据您的要求，删除了您近3个月所有关于负面情绪的Feed内容…已从您的Feed列表中永久移除…」 — both inventing before/after titles for feeds that were never touched. Neither case carries an answer assertion, so this ships today. It is the most user-damaging defect in the baseline, it is separate from the three original reds, and no amount of plan-shape or execution grading catches it — only an answer assertion does.

So the defect is not only "the planner never plans the write"; it is also "the suite cannot tell whether a planned write executed", "a planned write can carry a placeholder instead of the composed content", and "nothing checks whether the agent reports its own work honestly". A change that only makes `create_feed` appear in the plan would move the create-feed defect from a visible red to an invisible green — the worst outcome available.

The placeholders also settle a question this proposal originally got wrong. `"feed_id_from_list"` and the create-feed placeholder are not phrasing failures a better prompt can fix: a 4B planner at plan time has no way to know a real numeric feed id or the composed summary, so no prompt wording makes those values correct. Writes cannot work until the executor resolves values at execution time.

The score is the symptom. The stale corpus expectation, the hollow green siblings, and the deleted red tracker are the reason it survived five days.

## What Changes

- **Planner prompt: mandate the write tool for state-changing requests.** Add a rule to `PLANNER_SYSTEM_PROMPT` (`backend/agent_py/agent/planner.py:76-84`) requiring a matching registry `tool` step whenever the user asks to publish/create/update/delete a feed, and stating that an `llm` step composes text and never performs the write. Reconcile the rule with the existing `when unsure, prefer a single llm step` rule and add an explicit draft carve-out in the same edit. The fresh baseline shows the create case already plans the write; this rule is primarily for `main-all-tools-combined`. The create case is cleared by the corpus expectation update plus arg templating, with the guard's compose-before-write branch forcing the reference.
- **Deterministic planner guard: reject a plan that omits a required write tool, or plans a placeholder write.** Add a narrow check to the shared post-parse validation (`_enforce_plan_shape`). The missing-write branch fires only when the latest user message expresses an explicit state-change verb, contains no negation/draft qualifier, and the plan has no matching write tool — primarily `main-all-tools-combined`. The compose-before-write branch fires when a create/publish plan contains `create_feed` but no preceding composing `llm` step, or its args contain no reference to that step — the fresh `main-rag-create-feed` placeholder shape. Return `_PlanError("plan_invalid", ...)` so the existing `planner_retry_max` + `PREVIOUS_ATTEMPT_FAILED` loop re-prompts; do **not** inject a synthetic step, because a synthetic `create_feed`/`update_feed` step has no valid args and would fail schema validation. The check needs the latest user message passed into the post-parse path. It is a narrow lexical trigger, not a general intent classifier: it requires an explicit state-change phrase **and** a feed-composition-shaped final `llm` prompt for the missing-write branch, so a read/summary request such as 帮我查最近我发了什么 does not fire it; `main-rag-summary-recent` is the corpus canary. The legacy free-text planner path does not call `_enforce_plan_shape` and has no retry (`planner.py:555-557`), so the guard is structured-path-only until that path is unified; record that limitation rather than implying full coverage.
- **Execution-effect grading for state-changing cases.** Every write-expecting case (create, update, delete, and the combined chain) must grade the transcript's `tool_call`/`tool_result` frames, not only the plan: the named write tool must actually be called and its `tool_result.ok` must be true. Where feasible, assert the effect from the `tool_result` payload (the `create_feed` result carries the created feed) or the eval user's API (feed created/updated/deleted); for the create cases, also assert that the created feed's content reflects the retrieved data rather than a plan-time placeholder. This is deterministic and is the only assertion that can distinguish "planned the write" from "performed the write". Adding it will likely expose the currently-green update/delete siblings as red; that is the defect becoming visible, not a regression.
- **Settle the write-content mechanism before claiming user-visible success.** `_run_tool` executes the plan's static `step.args` (`backend/agent_py/agent/executor.py:277`); `_render_prior_data` feeds earlier `rag`/`tool` outputs into `llm` prompts only, never into tool args (`:575-628`). The fresh create case already plans the documented acceptable variant `[rag, llm, create_feed, llm]` (`docs_agent/AgentEvalPromptsRefine.md:39`), but the write args are static, so it publishes a plan-time title/description rather than the rag summary. Pick one: (a) add arg templating so a tool step can reference an earlier step's output and plan `[rag, llm, create_feed, llm]`; (b) grade a react-hosted write and expect `[rag, react, llm]`; or (c) scope this change to plan shape and explicitly disclaim user-visible publishing, filing the content fix as a follow-up. Do not ship (c) while claiming the user-visible fix.
- **Web tools prompt: prefer a flat `web_search` step for single lookups — deferred to `agent-web-single-lookup-routing`.** Extend `_PLANNER_RULE` (`backend/agent_py/agent/web_tools.py:520-524`) to prefer one `web_search` `tool` step and reserve `react` for requests needing multi-round iteration. Add an answer-content assertion on the force-search case that fires on the observed denial phrasing; note that `answer_forbidden` is a case-sensitive substring check, so the keyword must be one that actually appears in the failure (`无法获取` / `无法直接访问`), not the paraphrase `无法访问互联网`. The plan-shape requirement moves to that change's `agent-plan-shape-policy` delta; this change does not implement it.
- **Re-measure before optimising, and re-measure after.** The suite's last run is five days stale and the newest artifact on disk (`20261016T143912Z`) reads `1.00` off a 3-sample partial that exercised only the budget case — a false green. The fresh 2026-10-21 baseline (`baseline.md`, `evals/artifacts/20261021T174740Z/`) reproduces 0.73 and the three reds, but changes the create-feed diagnosis: the planner now plans the write and publishes a placeholder. Tasks require a clean baseline at current HEAD before any edit, a separate budget-stack baseline for the budget case, and a confirming run after.
- **Wire the eval suite's deterministic unit gate into CI.** `evals/tests` (corpus validation, graders, transcript parsing) needs no model and is currently unwired; `agent-golden-eval` already names this as new scope.
- **Restore open-red tracking and correct a false corpus note.** `bugs.md` was deleted with three open reds in it; `evals/cases/main.yaml` claims the update/delete siblings pass "on the same fixtures" when they use a different fixture set (food-\* vs mood-\*). Restore the diagnostics into the corpus case notes; do not reinstate a standalone tracker.

### Explicitly unproven

Every planner change above is a hypothesis about 4B behaviour, not a verified fix. Temperature 0 guarantees the *current* prompt→plan mapping is deterministic; it says nothing about a rewritten system prompt or a new deterministic guard. The projected rates — 30/33 = 0.9091 after the first prompt edit, 33/33 = 1.00 after both — are **arithmetic over passed/graded, not predictions**. The guard's verb list is a heuristic that can over-fire on draft/negation phrasing; the draft carve-out and its case are the tripwire. If the edits do not flip the model, they ship unproven; a non-improving re-run is a recorded outcome, not a reason to keep tuning until the number moves.

### Decision points for the reviewer

1. **Write-content mechanism — RESOLVED: (A) arg templating.** Operator decision 2026-10-22; rationale in `design.md` Decision 4. This is not create-feed content polish — it decides whether feed mutation works at all, because the placeholder ids in the update/delete cases cannot be produced by any prompt wording and only execution-time resolution supplies a real one.
2. **Plan-shape-only vs execution-effect grading — RESOLVED: execution-effect grading.** Adopted by this change; the spec delta and tasks require it for every write-expecting case. Without it the change cannot prove the user-visible fix, and the existing update/delete greens remain hollow.
3. **Corpus strictness.** `docs_agent/AgentEvalPromptsRefine.md:39` originally listed `[rag, llm, tool:create_feed, llm]` as an acceptable variant; on 2026-10-16 an operator overrode it to the strict form at `evals/cases/main.yaml:37`. The compose-then-write route adopted in Decision 4 moves the corpus to the compose-then-write variant, so this is settled by that decision rather than left open.
4. **Update/delete siblings — RESOLVED: fixed in the slice sequence, not in this change.** Operator decision 2026-10-22. The cases ask for a *plural* mutation ("所有关于不好情绪的feed") and the tools are strictly single-target, so this needs the bulk write tools rather than a prompt rule. This slice adds the execution assertions that make the current hollow green honest and records the two cases red with operator sign-off; the fix lands in the Go-only sibling `agent-feed-bulk-write-tools`, which turns them green. Recording them green while the writes never execute is the pattern this change exists to close.
5. **How a bulk write selects its targets — RESOLVED: by query, not by id.** Operator decision 2026-10-22; rationale in `design.md` Decision 4b. The planner can author a query from the user's own words and cannot author an id, so query-based arguments are the only ones expressible at plan time. This lands in a Go-only sibling change (`agent-feed-bulk-write-tools`). This change's execution assertions do not depend on the sibling: they assert that the write actually executed, so they will record the current single-target cases red; the sibling is what turns them green afterward.
6. **Ordering: per-case fixes before that case's assertions.** Land a case's write fix before tightening that case's gate: create templating lands here, so the create-case assertions land here; the update/delete fix lands in `agent-feed-bulk-write-tools`, so their assertions land here as honest red and the sibling flips them green. The update/delete red is deliberate and recorded, not an accidental side effect of tightening the gate early.

## Slicing

This change is slice 1 of two. It takes the main line 0.727 → 0.545 → ~0.75: the rate barely moves, and that is the point — two hollow greens become honestly red while the create-feed defect gets fixed.

Slice 2 is two changes, sequenced together by operator decision (2026-10-22) rather than by technical coupling:

- `agent-feed-bulk-write-tools` — Go-only. The query-based bulk write tools and the update/delete fix (0.727 → 0.909 on the original 33-sample denominator).
- `agent-web-single-lookup-routing` — Python-only. The `web_search` single-lookup rule and the react data-flow gap that clears `main-web-force-search` (0.909 → 1.00 on the original 33-sample denominator). These slice-2 figures use the original denominator; slice 1 adds the draft case's three samples, so the actual per-slice rates differ.

Neither slice-2 change has an implementation dependency on this change; the web change's spec delta does require this change to archive first so the `agent-plan-shape-policy` capability exists. This change's execution assertions are what make the bulk tools' need visible. Keeping them as two changes rather than one means the Go work and the Python work can land in either order and neither drags the other.

Slice 1 deliberately ends with **three** red cases — the same count it starts with, but a different and honest set. `main-rag-create-feed` and `main-all-tools-combined` turn green; `main-rag-update-feed` and `main-rag-delete-feed` go from hollow green to real red, recorded red and operator-signed per the `agent-golden-eval` sanity rule; `main-web-force-search` is untouched and deferred to slice 2. Deferring a known fix is acceptable; leaving a hollow green is not.

## Capabilities

### New Capabilities

- `agent-plan-shape-policy`: which step kinds the planner must choose for a given request shape — the write-tool mandate for state-changing requests, the draft/negation carve-out, and the deterministic rejection of a plan that omits a required write tool. No existing capability specifies plan *content* policy; `agent-planner-structured` governs plan *emission mechanics* (structured binding, validation, retry), and `agent-web-tools` / `agent-tool-registry` treat both `tool` and `react` as equally valid hosts for `web_search`. The single-lookup web rule is added to this capability by `agent-web-single-lookup-routing` after this change archives.

### Modified Capabilities

- `agent-golden-eval`: (1) a case may carry plan-shape *and* answer-content assertions together, and a plan-shape-only case leaves answer quality ungraded by construction; (2) state-changing cases grade execution (`tool_call` name + `tool_result.ok`, plus the DB effect where feasible), not just plan shape, and a write-expecting case declaring no execution assertion is a corpus bug; (3) the deterministic unit gate runs in CI; (4) the overall floor records its provenance — the applied floor and the baseline rate it was derived from — and a partial run is never recorded as a baseline.
- `agent-loop`: a `tool` step's arguments may reference an earlier step's output and are resolved by the executor at execution time, failing closed on unknown, forward, or cyclic references, with untrusted-content handling applied to resolved values at the dispatch boundary. This is where arg templating lives — it changes tool-step execution semantics, not plan shape.

## Impact

- **Code**: `backend/agent_py/agent/executor.py` (arg-template resolution pass + untrusted-content handling on resolved args — **now in scope** per Decision 4), `backend/agent_py/agent/planner.py` (system prompt rules + reference syntax + deterministic guard + latest-user-message plumbing), `evals/cases/main.yaml` (re-shaped create expectations, execution assertions, answer assertions incl. the hallucinated-success case, corrected note, draft case, floor re-derivation), `evals/graders/` (execution-effect grader; answer assertions already exist), `evals/tests/` (grader and corpus tests), `.github/workflows/ci.yml` (unit-gate job + path filters), root `Makefile` (floor provenance). `backend/agent_py/agent/web_tools.py` and the force-search answer assertion move to `agent-web-single-lookup-routing`.
- **Security surface introduced**: arg templating routes attacker-influenceable content (retrieved feed text, fetched web pages) into mutating tool arguments. The resolution pass gets a dedicated security review and normative untrusted-content handling at the dispatch boundary before merge; see `design.md` Risks and the `agent-loop` delta.
- **Behaviour**: user-visible. A request to publish a feed must actually publish the requested content, and a request that names web search must return search-derived answers. Plan-shape grading alone does not establish either.
- **Out of scope**: no Go backend changes, no frontend changes, no `.env*` edits, no changes to `agent-tool-registry` (the tools already dispatch correctly — the planner just never calls them, or calls them with invalid args), no corpus relaxation unless the reviewer chooses it, no LLM judge, no scheduled live eval run.
- **Rollout gates**: none. No production env flip, no deployed-stack smoke, no multi-day green window. If the reviewer additionally wants a "green across N consecutive nightly runs" sign-off before trusting a scheduled live eval, that window is rollout-shaped and belongs in a `-rollout` sibling — but no such gate is claimed here, and the scheduled-run task is scoped to a feasibility spike with a documented manual fallback instead.
