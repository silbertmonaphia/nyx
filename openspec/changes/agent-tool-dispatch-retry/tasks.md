## 4. Transient-failure retry path

- [x] 4.1 In `backend/agent_py/agent/executor.py`, add a second retry loop around the same `tools.call` site for transient errors (network timeout, 5xx, 408, 429). Backoff: `min(base * 2^attempt + jitter, ceiling)` with `base=250ms`, `ceiling=5s`, jitter ±20%. The two retry paths MUST NOT both fire on the same error — a validation error routes to the tool-arg path, a transport error routes here. **Implemented** — `_classify_tool_failure` + `_compute_backoff_ms`; `tools_client.py` maps 408/429 → `ToolUnavailableError` and bare 4xx → the new non-retryable `ToolRejectedError` (4xx bodies carrying a JSON-RPC error envelope remain `ToolError` = registry rejection → arg path).
- [x] 4.2 Add `test_executor_retries_on_transient_failure` — first `tools.call` raises a network timeout, second succeeds. Assert `agent_tool_retries_total{tool, reason="tool_execution_transient"}` increments by 1 and the eventual `tool_result` carries `retry_count=1`. **Verified** — also asserts the model is NOT re-invoked on this path.
- [x] 4.3 Add `test_executor_terminates_step_on_persistent_transient_failure` — every `tools.call` raises a 503. Assert the step ends with `step_failed`, the mapped error reaches the user (no internal text), and the counter increments by `tool_retry_max` (not `+1`). **Verified** — terminal wire text is the static "tool unavailable"; the transport message never reaches the frame.
- [x] 4.4 Add `test_4xx_non_retryable_fails_fast` — `tools.call` raises a 400. Assert no retry occurs, `agent_tool_retries_total` is not incremented, the step fails immediately. **Verified** — one attempt, both reason counters unchanged, terminal frame carries "tool call rejected (HTTP 400)".
- [x] 4.5 Add `test_validation_error_routes_to_arg_path_not_transient` — a typed validation error MUST NOT trigger the transient retry loop, even if it happens to be raised at the transport layer (e.g. the bridge returns 422 with a Pydantic error body).
