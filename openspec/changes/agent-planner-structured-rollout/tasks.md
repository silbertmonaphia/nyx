## 2. Browser e2e

- [x] 2.1 Playwright run — from `agent-planner-structured` 7.x. Full stack up; `cd frontend && npm run test:e2e -- tests/e2e/chat-agent-planner.spec.ts`. Verify green; if red, record the failure verbatim here (model nondeterminism is a finding, not a reason to loosen silently).
  **PASS (2026-10-13) after two spec fix-iterations.** Both initial failures were spec bugs against intended UI behavior, not planner defects: (a) the agent-steps `<details>` auto-expands while steps run and auto-collapses on settle (`ChatPanel.tsx:243 open={hasRunningSteps}`), so post-settle assertions must re-expand it — the click a user makes to inspect a finished trace; (b) `.locator('summary')` is a descendant query that also matches each tool row's nested `args` `<details><summary>`, tripping Playwright strict mode — the spec now clicks `:scope > summary`. The live model emitted the `list_feeds` tool step on every run (14× DOM resolutions observed even in the failing run). Final: `3 passed` (live tool-step path + the two §2.2 replays).
  **Suite-wide regression finding (fixed):** running the *full* e2e suite surfaced that `chat-rag` / `chat-empty-bubble` / `chat-agent-planner` all declared `TEST_USER` at module level while registering in `beforeEach` — any worker executing a second test from the same file re-registered the same username → `409 "User already exists"` → no success toast (measured with wire probes; the intermittent, worker-count-dependent flake that predates this change). Fixed with per-test `makeTestUser()` factories in the three specs; a temporary auth-429-retry fixture built while the cause was unknown was removed (the rate limiter was innocent; 15-simultaneous synthetic registers did show 5×429, but the suite never trips it). Post-fix: full suite green twice consecutively (15 passed, ~11 s each), serial 14/15 (the 15th = residual flake below).
  **Residual flake (pre-existing, documented, not this change):** occasional multi-second stack-wide slowdown windows (unexplained; GPU idles at 0% and agent runs take ~1.3 s outside them) can push two fixed-5s pre-existing asserts past their budget — feed-crud's update-refetch assert and a register-toast assert. Observed ~1/10 runs; both specs untouched by this change; candidate follow-up = timeout hardening or root-causing the WSL2/GPU-PV slowdown bursts. Not a blocker: the planner spec passed in every full-suite run.
