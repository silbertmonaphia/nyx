# Design

## Context

The feed RAG path is mature and measured. `internal/rag` owns an embedder (per-user BYOK resolution, SSRF-guarded dial, width check), an indexer (sha256 no-op skip, embed-on-write), a retriever (pgvector cosine top-K, user-scoped on both sides of the join), a service (embed → retrieve → render a truncated context block), and a bridge handler at `GET /internal/rag/retrieve` that the Python agent calls. `feed_embeddings` is a `feed_id`-keyed table with one row per feed — **there is no chunking**: `rag.ChunkText` is `Title + "\n\n" + Description`, and the whole thing becomes one vector. The recall baseline in `internal/rag/recall_integration_test.go` measures recall@5 = 0.944 over 68 hand-labelled Chinese queries.

A knowledge corpus breaks that shape on four axes at once: the unit is a file rather than a snippet, the text is long and structured rather than short and flat, the lifecycle is a filesystem rather than CRUD, and a passage must be attributable to a location. The reuse is real — same embedder, same BYOK resolution, same pgvector pool, same HNSW opclass, same bridge, same SSE frames — but the storage shape and the chunking are genuinely new work.

The corpus that motivates this is a categorized notes tree (`posts_douban`): 42 Markdown files under `A-`, `B-`, `P-`, `W-` prefixed directories, mostly Chinese, each file carrying a title and one to several `#`/`##` sections. That structure is the design driver: the directories are the natural retrieval scope, and the sections are the natural chunk boundary.

See proposal.md for motivation; behavior contract in specs/{kb-sources,kb-ingestion,kb-retrieval} and the deltas to specs/{agent-rag-bridge,agent-loop}.

## Goals / Non-Goals

**Goals:**

- A second corpus that coexists with the feed corpus without touching the feed vector table.
- Structure-preserving chunking that keeps a passage attributable to a file and a section.
- A source model that separates an operator-managed shared directory from per-user private directories, with private paths operator-confined.
- **Two editing models that do not fight each other**: a document the user manages on disk stays file-backed (the application refuses to edit it), and a document the application owns is stored inline and is editable in place — with the retrievable content flipping only once the new version is fully indexed.
- **One-shot import of a corpus that already exists**, as an operator command rather than a per-user request.
- Reuse of the existing embedder, BYOK resolution, pgvector pool, bridge and SSE frames.
- An agent that can search the knowledge corpus deliberately — scoped to a source or a directory — and cite what it found.

**Non-Goals:**

- PDF / DOCX / HTML ingestion in this change. v1 is Markdown only; the seam for the others is designed here and specified, but the implementations land later.
- Lexical / BM25 second retrieval leg. The feed recall baseline found no measurable gap from a lexical leg on the feed corpus; a KB corpus is a different corpus, so the question is re-opened once there is a KB recall baseline to measure against. `pg_trgm` is already enabled in this deployment (migrations 000006/000007 gave the feed columns trigram indexes), so the leg is available later without a new extension — but Postgres `tsvector` is the wrong tool for a Chinese-dominant corpus, since it does not segment Chinese.
- Object storage for uploads. The corpus is small and the upload body is stored inline with the document (D13); the storage boundary is a seam.
- A shared/mega chunk table holding both corpora.
- Cross-corpus ranking calibration. Fusion is by rank (D8).
- Migration of the feed corpus to the new shape.

## Decisions

**D1 — The knowledge corpus is a separate corpus with its own tables; `feed_embeddings` is not touched.**
`feed_embeddings` is keyed by `feed_id` with a foreign key to `feeds`, its embedding column is `NOT NULL`, and it carries one HNSW index over one embedding column. A chunk row needs a document identity, a heading path, a locator, a nullable embedding (D4), and a per-chunk hash — none of which fit that shape without dropping the FK and rebuilding the index on a live table. Migration 000015 already paid the cost of an HNSW rebuild once, for a dimension change; paying it again to widen a table for a second corpus is a blast radius with no benefit.
*Alternative considered*: one polymorphic `chunks(source_type, source_id)` table serving both corpora — rejected. It loses the FK, forces one HNSW to serve two access patterns with different selectivity, and puts a migration on the live feed vector table to buy cross-corpus fusion that D8 solves at query time for free.

**D2 — Three tables: `kb_sources`, `kb_documents`, `kb_chunks`.**
`kb_sources` is "where content comes from, and who may see it": scope, owner, display name, kind (`dir` | `inline`), root path (present only for `dir`), enabled. `kb_documents` is one document: its source, scope/owner, origin (`file` | `inline`), relative path, title, type, content hash, byte size, mtime, status, generation, and — for inline documents — the authoritative body. `kb_chunks` is one embedded unit: its document, scope/owner/source (denormalised), generation, ordinal, heading path, body, embedded text, hash, embedding, embedding model, token count, locator.
Why a source table rather than columns on the document: the visibility rule and the path-confinement base are properties of the *place*, not of each file; a user may have several private roots; and application-created documents still need a home so that the visibility join stays uniform — an `inline` source per user holds them, carrying no root path.
The `generation` column is what makes the swap atomic (D4): a document's retrievable content is the chunk set of its current generation.

**D3 — Visibility is `scope` + `owner_id`, denormalised onto both documents and chunks.**
A chunk is filtered on its own `scope`/`owner_id` columns — no join on the hot path, mirroring why `feed_embeddings` denormalises `user_id`. The retriever still JOINs `kb_documents` back and re-asserts that the document's scope and owner equal the chunk's, the same defence-in-depth the feed retriever applies (`queries/rag.sql` filters `fe.user_id`, `f.user_id` and `f.deleted_at IS NULL`). Rule: `scope = 'shared'` is visible to every caller; `scope = 'user'` is visible to its owner only.
*Alternative considered*: derive visibility by joining `kb_sources` — rejected for the hot path, kept as the source of truth that the denormalised columns must agree with.

**D4 — Index before embed, and swap generations only when the new content is fully embedded.**
The feed path embeds before insert because a feed is one vector and the write is user-visible: a failed embed must not leave a half-written feed. A knowledge ingest produces hundreds of chunks from one file; if the embedding call fails halfway, re-running the parse is pure waste, and the user has already waited. So the parse and the chunk write happen first, the embedding fills afterwards through a best-effort claim (`UPDATE … WHERE embedding IS NULL … RETURNING`; the row lock does not span the embedding call, so concurrent workers may repeat a chunk and the write is idempotent), and a failure leaves the document `pending` with its chunks already stored.
Chunk-writing alone is not enough, because "the old chunks are replaced by new, unembedded ones" means a failed embed makes the document *vanish* from search — the worst possible outcome for a knowledge base, and precisely the failure mode an in-place edit must not have. So a document carries a **generation**: a re-index writes the new chunks at generation *N+1* while the document stays at generation *N*, and the document advances only once the new generation is fully embedded. Retrieval filters `chunk.generation = document.generation`, so the corpus always serves a completely-indexed version of every document — the previous one while the replacement is pending. Chunks from superseded generations are deleted after the swap.
Cost: `kb_chunks.embedding` is nullable (unlike `feed_embeddings.embedding`), the retrieval query filters `embedding IS NOT NULL` *and* the generation, and the fill pass must be scoped to the pending generation rather than to every unembedded chunk. All three are explicit in the delta.
This also makes the fill pass the natural place to enforce the embedding-identity rule that `feed-embed-indexing` already owns for feeds — when the user's embedding model changes, the KB vectors are invalidated the same way.

**D5 — Chunking is heading-aware, and the embedded text carries a context header.**
Rules: a chunk belongs to exactly one heading path and never spans two; within a path, blocks are packed to a target token budget under a hard cap; tables are never split (an oversized table splits by rows with the header repeated); fenced code blocks are never split — a fence larger than the cap is still kept whole, because the cap is a packing budget for splittable content, and a fence too large for the embedding window leaves the document pending with the reason visible rather than truncating code; a section below the minimum size is kept rather than dropped and still carries its heading; overlap does not cross a heading boundary. Image references contribute their alt text as ordinary text and never their URL (the alt caption is the only semantic signal an image carries; the URL would be vector noise, and v1 deliberately reads no binary content).
The embedded text is `rel_path › heading_path` followed by the body; the body alone is stored separately for citation. This is the single largest recall lever available: a chunk from `B-Cook/2019-11-16-Cook-Diet.md › 煮食记 / 碳水列表` embeds with that prefix, so its vector carries *where* the text came from, not just what it says. Without it, a chunk saying "一份碳水 + 一份蛋白 + 两份蔬菜" is nearly indistinguishable from any other chunk saying the same thing.
Budget: the local embed server runs with `--max-model-len 2048`, so the hard cap (default 700 tokens) leaves ample headroom, and the target (default 400) keeps most chunks well clear of it.
*Alternative considered*: fixed-size sliding windows — rejected. They slice across heading boundaries, discard the section semantics that make the corpus navigable, and produce chunks whose vectors say nothing about where they came from.

**D6 — One normalizer seam; Markdown is the only v1 implementation.**
`Normalizer{Handles(docType) bool; Normalize(ctx, raw, src) (*Document, error)}` returns a flat, ordered block list whose blocks carry a heading path, a kind, and a locator. v1 registers only the Markdown implementation. The chunker, the store, the indexer and the retrieval path are written against the block list, not against Markdown, so adding a format later adds one implementation and one `docType` case — nothing else moves.
Runtime: Go for v1. The PDF/DOCX ecosystems in Go are weak (pdfcpu loses heading structure; `lufia/docx` loses styles and tables), so the later formats are planned as a normalizer implemented in the Python service behind a new route, reached by Go over the service token — the Go→Python direction already exists (`chat.NewAgentProxy`, `X-Nyx-Service-Token`), so no new deployment unit is introduced.
v1 deliberately ships **no binary parser**: an untrusted PDF/DOCX parser is a materially different attack surface from a text normalizer (zip bombs, decompression bombs, image decoders), and it is not needed to prove the pipeline. That decision also keeps the path-validation story simple — the only filesystem content the v1 server reads is text it will display as text.

**D7 — Change detection is at the document level; chunk hashes are stored for a later refinement.**
A document's content hash is sha256 of the content it was indexed from — the raw file bytes for a `file` document, the stored body for an `inline` one. Unchanged → skip the document entirely, zero embedding calls (the same no-op guard the feed indexer uses). Changed → re-chunk and re-embed at the next generation (D4). Removed from disk → its chunks go away and it stops being retrievable.
Why document-level for v1: heading-aware chunking has no stable identity for "this chunk, across edits". Chunk *n* of the old file may correspond to a different region of the new file, so a chunk-level diff would need content-addressed chunk identity plus heading-path alignment to be correct. Storing the per-chunk hash now means that refinement is a query change later, not a re-parse of history.

**D8 — Corpus selection is explicit; `both` fuses by rank, not by score.**
The bridge takes `corpus=feeds|kb|both` (absent means `feeds`). `feeds` is byte-identical to today. `kb` searches the knowledge corpus with optional `source` and `path` filters. `both` takes the top-K from each corpus and combines them with Reciprocal Rank Fusion.
Why RRF: the two corpora are not on a comparable similarity scale. A feed snippet and a document chunk have different lengths, different topical spread, and different score distributions, so `score_a > score_b` across corpora is not a meaningful comparison. RRF consumes only each passage's *rank within its own corpus*, which is scale-free and needs no calibration constant.
*Alternative considered*: one vector query across a merged table — rejected (D1). *Alternative considered*: normalising the two score lists (z-score / min-max) before merging — rejected as a fitted constant with no principled value; rank fusion has none.

**D9 — The citation envelope becomes a tagged union, extended additively.**
Today each citation is `{feed_id, snippet}` and the shape is frozen in `agent-rag-bridge`. A knowledge citation needs the source name, the relative path, the heading path, and the locator. The envelope keeps `context_block` and `citations`; each citation gains a `kind` discriminator (`feed` | `doc`); a feed citation keeps its identifier in `feed_id`; a knowledge citation carries `feed_id: 0` plus `doc_id`, `source_name`, `rel_path`, `heading_path`, `locator`. The Python client keeps reading `citations[].feed_id`, so the existing consumer is not broken, and the existing "never `null`" rule is preserved.
Because this is a spec-frozen wire shape, it ships as a delta to `agent-rag-bridge`. Per the repo's wire-contract rule, the change must include a test in which the **Python** parser consumes the **Go** producer's bytes — two sides each asserting their own shape is the classic way both sides stay green while both are wrong.

**D10 — The agent gets a new `kb` step kind rather than a corpus parameter on `rag`.**
`agent-loop`'s step-kind requirement names `rag` as "vector retrieval over feeds" and the planner prompt repeats that `rag` is for the user's feed data. A corpus parameter would make one step kind mean two things and would make the `step_start` frame ambiguous about what was searched. A distinct `kb` kind keeps the plan self-describing, keeps the planner prompt honest, and reuses the existing `step_start`/`step_end` frames — no new SSE frame kinds.
A `kb` step carries `query`, optionally `source` and `path`. The planner is given a knowledge outline (per visible source: id, name, scope, document count, chunk count, top-level directory names) so it can narrow a query to a directory instead of searching everything. Without the outline the planner cannot know that `B-Sport/` exists, and the directory taxonomy — the main organising principle of a notes tree — would be invisible to it.

**D11 — Indexing triggers: explicit, plus a bounded lazy catch-up.**
Explicit trigger: the caller asks for an index over the sources visible to them (their private sources plus the shared source). The hash skip makes a repeat scan cheap — a rescan of an unchanged tree costs file reads and hashes, no embedding calls.
Lazy catch-up: a chat request that observes a `pending` document or an unembedded chunk starts a background fill on a detached context, bounded per invocation. This is deliberately the same shape as `rag.Service.BackfillOnce` — a detached context, a per-user once-guard, a bounded batch — because it is the same problem: the user should not wait for indexing to answer a question.
*Alternative considered*: a filesystem watcher — rejected. Bind mounts, network filesystems and WSL all make inotify unreliable, and the hash-based scan is already cheap at this scale. *Alternative considered*: a periodic ticker — deferred; it adds a background loop, a scan lock and a failure mode that the explicit trigger plus catch-up already covers.

Consequence, stated plainly because it is a product-visible behaviour: **discovery is pull-based.** A file edited on disk is noticed at the next explicit index, not before it. The chat-time catch-up fills pending and unembedded work; it does NOT re-hash the tree, because re-hashing on every chat turns a chat request into a filesystem walk. So between an edit and the next explicit index, the corpus serves the previous generation of that document (D4 keeps it served rather than dropped — it is stale, not missing). If the desired behaviour is "edit the file, ask a question, get the new text", the catch-up must also re-hash, which is bounded by a time window or a file-count budget; that is an open question below.

**D12 — A document's origin decides where its truth lives and whether the application may edit it.**
Two origins, one pipeline. A `file` document's authoritative content is a file on disk: the application never writes it, and an attempt to edit it through the API is refused with a static message naming no path — the user is told, in effect, to edit the source file. An `inline` document's authoritative content is stored with the document itself: the application owns it, and editing it in place replaces the body, re-chunks and re-embedds it, keeping the document's identity.
Why the split rather than one model: the motivating corpus is a notes tree the user already manages elsewhere (an editor, a git repo, an outliner) — for that corpus, file-as-truth is the whole value proposition, and an application that could "helpfully" rewrite those files would be worse than useless. But an uploaded document in a hosted deployment has no file the user can reach, so file-as-truth would make uploads permanently read-only. One model cannot serve both; the origin field serves both with one chunking and one embedding pipeline.
The refusal for a `file` document is not a limitation dressed up as a rule — it is what keeps the two models from silently corrupting each other. If the application could edit a file-backed document, the next scan would overwrite the edit with the file on disk, and the user would lose data with no error.
*Alternative considered*: file-as-truth for everything — rejected, it makes uploads read-only in a hosted deployment. *Alternative considered*: database-as-truth for everything — rejected, it gives up "the file I edited is the truth", which is the property that makes a notes tree worth indexing at all.

**D13 — An upload stores the body inline; there is no upload sink on disk.**
`POST /api/kb/documents` accepts a Markdown file, sniffs the bytes as text/Markdown (the extension and the client's declared content type are not trusted), stores the body as an inline document owned by the uploader in that user's `inline` source, and indexes it. The upload is not written to the filesystem, so no upload-sink path is configured and no second storage model exists.
The consequence is that "upload" and "create a document in the application" are the same operation: both produce an inline document under the same edit model (D12), and both are editable afterwards. A document created empty and typed into is not a second feature — it is the same row with a different first write.
Object storage is deferred deliberately: the corpus is small, the storage boundary is a seam, and the inline body column needs no bucket, no credentials and no signed-URL story. When binary formats arrive (Phase 2), a blob column or an object store becomes necessary and the inline model is where it lands.

**D14 — Bulk import of a historical corpus is an operator command, not a caller request.**
The motivating case is a corpus that already exists on disk and has to be ingested once — 42 Markdown files, ~350KB, a few hundred chunks, a couple of hundred seconds of embedding. That is an operator action: it writes into the shared scope, it makes a directory readable by every user, and it needs no caller identity. So it gets its own binary, `cmd/kb`, with an `index` subcommand that takes a root directory and a `--shared` flag, plus a `status` subcommand that prints the corpus shape.
The flag is not default: creating a shared source is a trust decision — it makes a directory of the operator's choosing visible to every user of the deployment — so it must be typed explicitly, and the command prints what it is about to expose before it does.
The per-user API trigger stays for the other case: a user pointing the application at their own directory wants a re-index of *their* corpus under *their* embedding identity, with no shared-scope side effect. The two operations share the same ingest pipeline and differ only in scope and embedding identity.
*Alternative considered*: doing the bulk import through the per-user API trigger — rejected. It would either need an operator to act as a user, or it would make the shared source's identity depend on whichever user happened to trigger it.

**D15 — The shared corpus carries one embedding identity, and a caller in a different space sees none of it.**
A private corpus is indexed with its owner's embedding model, so it lives in that owner's space and is queried in the same space — the feed corpus already works this way. The shared corpus is different: it is indexed once, under the deployment's embedding identity, and every user queries it with their own. When a user's stored embedding configuration differs from the deployment's, their query vector is in a different latent space and the shared corpus's vectors are meaningless against it — the same failure `rag.Retriever`'s contract already warns about ("calling Retrieve with a vector from a different embedding model returns garbage rankings"), except the feed corpus never hits it because a feed is always indexed by its own owner.
So the chunk's recorded embedding identity becomes a retrieval predicate, not just an observability field: a chunk is returned only when its recorded identity matches the identity that produced the caller's query vector. A user with a different BYOK model still gets their own private corpus and their feeds; they simply do not see the shared corpus.
This also fixes a subtler variant of the same bug: two different 1024-dimension models pass the width check and fail only on semantics.

## Risks / Trade-offs

- [A private root is a TOCTOU window between save and scan] → validated at save time AND re-validated at scan time; the scan resolves the real path again and refuses anything outside the base, so a root replaced by a symlink after saving is caught at the moment it is used. The cost is that a legitimate reorganisation of the private base breaks the source until the path is re-saved — which surfaces as a recorded reason on the source, not a silent empty result.
- [Document-level re-chunking re-embeds a whole file on any edit] → acceptable at knowledge-corpus scale (a file is typically under a dozen chunks). The per-chunk hash is stored so a later refinement can narrow the re-embed to the chunks whose content actually changed.
- [The generation counter is extra machinery on every write and every read] → the alternative is a document that disappears from search whenever its re-embed fails, which is a worse trade for a knowledge base. The cost is one integer column, one filter in the retrieval predicate, one swap statement, and a garbage-collection rule for superseded generations.
- [Two editing models mean the UI has to explain which is which] → the origin is surfaced on the document card, and a file-backed document's edit control is disabled with a message pointing at the source file, rather than being hidden.
- [Two corpora means two places for the model to look] → the planner decides, and the outline makes the decision informed. The alternative — silently merging the corpora into one result list — would hide the distinction from the user and make the citation ambiguous.
- [Fusion by rank discards score information] → deliberately. The scores are not comparable across corpora (D8), and rank is the part that is comparable. A single-corpus request still returns scores.
- [The embedding model identity has to be tracked per chunk] → `kb_chunks.embedding_model` exists for exactly the reason `mem0_prep.md` §6 records for preferences: a silent model swap desyncs a vector store, and the desynced rows must be findable, not discoverable by accident.
- [Chinese exact-term recall may be weaker in a long-form corpus than in a snippet corpus] → not asserted either way without a measurement. The change ships a KB recall baseline with hand-labelled queries so the question can be answered with data; if it turns out a lexical leg is needed, `pg_trgm` is already available and the retrieval path has a filter seam for it.
- [A second vector store doubles the operational surface] → accepted. The alternative (one table for both corpora) puts a migration on the live feed vector table, which is the larger operational risk.
- [The shared corpus is invisible to a user whose embedding identity differs (D15)] → by design, and it fails safe (no garbage passages, just an empty shared source). The knowledge-base page must say *why* the shared source shows no passages rather than leaving the user to guess.
- [Deleting a source removes everything indexed from it] → the blast radius is the caller's own corpus, and the shared source cannot be removed through the caller-facing API. The operator's `kb` command is the only path that removes shared content.
- [The operator import command is a second entry point into the ingest pipeline] → it calls the same pipeline function as the API trigger; the difference is scope and embedding identity, not a parallel implementation. The pipeline is exercised by the same tests either way.

## Migration Plan

Default-off: `KB_ENABLED` unset means no KB tables are written, no source is scanned, and no knowledge retrieval is offered — behaviour is identical to today. Enabling requires the operator to set `KB_ROOT` (the shared directory) and `KB_PRIVATE_BASE` (the per-user confinement root) and to make those paths readable by the backend process; the migration itself adds three tables and one HNSW index and does not modify `feed_embeddings`. Rollback is to unset `KB_ENABLED` and restart — the tables can be left in place, and dropping them is a separate, explicit operation.
Changing the user's embedding identity invalidates their stored vectors; the KB follows the same rule as feeds (`feed-embed-indexing`, "Changing the embedding identity invalidates stored vectors"), so the KB's invalidation hook runs alongside the feed one when the embedding configuration is replaced. The shared corpus is indexed under the deployment's embedding identity (D14, D15); changing the deployment's embedding identity invalidates the shared corpus's vectors and it must be re-imported by the operator.

## Open Questions

- **Should the chat-time catch-up also re-hash the tree?** Today discovery is pull-based (D11): a file edited on disk is noticed at the next explicit index. The alternative is for the catch-up to re-hash the source tree on a chat request, bounded by a time window or a file-count budget, so an edit is picked up within a conversation. The cost is turning a chat request into a filesystem walk, which does not scale with the corpus. This needs a decision before the implementation lands; the spec currently states the pull-based behaviour.
- **A reranker or a lexical leg is deliberately absent, pending the KB recall baseline.** The feed baseline (recall@5 = 0.944, dense-only) measured no lexical-recall gap; its only imperfect queries were crowded at ranks 6–10 — a rerank/top-k problem, recorded but deliberately not fixed in the measurement-first round. The same question stays open for the KB corpus until the baseline in task 12.2 lands: if gold passages cluster outside the top-5, the next change is a reranker behind the retrieve seam or the `pg_trgm` lexical leg (extension already enabled, filter seam reserved). The two stages compose without contract churn: D8's fusion is a pure rank function over N ranked lists, so a future BM25 leg either fuses as an additional list (preserving more signal than pairwise fusion) or composes per corpus first — the bridge's `corpus=` contract and the spec's "combine by rank, not score" wording pin neither choice, and no `k` constant is frozen. A legal-style corpus (statute numbers, terms of art) is the likeliest future trigger for the lexical leg; a customer-support or notes corpus decides from its own baseline numbers.
- Deferred to the follow-up that adds non-Markdown formats: whether the PDF/DOCX normalizer runs in the Python service as planned (D6) or in a separate sandboxed worker, and whether a scanned PDF without a text layer is rejected or routed to OCR.
